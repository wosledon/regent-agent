# Regent-Agent 待确认项

> 用途：统一记录尚未确认的产品、架构、安全、运营和商业化决策。  
> 状态：待逐项讨论  
> 编号：`Q-001` 起，长期保留，不因确认后重新编号。

## 1. 使用规则

1. 每次只讨论一个编号，避免多个决策混在一起。
2. 每项最终状态只能是：`待讨论`、`已确认`、`采用默认值`、`已否决`、`已延后`。
3. 确认后必须记录结论、理由、影响文档和验证方式。
4. 已确认项同步进入 PRD、技术设计或对应详细设计；本文只保留决策索引。
5. 新发现的待确认项追加到末尾，不插入旧编号。

推荐记录格式：

```text
编号：
结论：
理由：
影响文档：
默认值或回退方案：
验证方式：
状态：
```

## 6. Q-001 决策记录

### 6.1 解决与升级原则

- 员工遇到问题先在当前层解决，再沿组织树逐级向上：直接上级 → 更高层 Leader → Controller → Boss。
- 内部升级属于正常自治机制，不计为人工介入，但必须记录次数、耗时和结果。
- 只有内部链路确实无法解决的问题才提交 Boss；必要审批仍单独统计，不算失误。
- 所有已发生的失误、错误重试、错误交接、质量缺陷和无效尝试都必须记录，即使后续修复也不能从指标中抹除。

### 6.2 指标口径

| 指标 | 定义 |
|---|---|
| 一次自主通过率 | 无失误、无错误重试、无内部升级、无 Boss 升级即达到退出门禁的尝试占比 |
| 最终自主完成率 | 允许内部逐级解决，但最终无需 Boss 救援即完成的比例 |
| 内部升级率 | 发生员工沿组织树向上升级的尝试占比 |
| Boss 升级率 | 内部无法解决而需要 Boss 决策或救援的尝试占比 |
| 失误率 | 每次尝试中已发生失误的数量或占比；修复后仍保留 |
| 必要审批率 | 预算、发布、红线等制度要求的 Boss 审批占比，不计入失误 |

### 6.3 初始试运行目标

| 阶段 | 一次自主通过率 | 最终自主完成率 | Boss 升级率上限 | 目标耗时 |
|---|---:|---:|---:|---:|
| R1 自主启动 | ≥90% | ≥95% | ≤10% | ≤15 分钟 |
| R2 自主调研 | ≥60% | ≥80% | ≤20% | ≤4 小时 |
| R3 自主交付 | ≥30% | ≥70% | ≤30% | ≤72 小时 |
| R4 治理与运营 | ≥95% | ≥98% | ≤5% | 按动作时限 |
| R5 SaaS 启动 | ≥95% | ≥98% | ≤5% | ≤15 分钟 |
| R6 开源自托管 | ≥99% | ≥99% | ≤10% | ≤30 分钟 |

- 以上为 dogfooding 初始值，至少积累 10 次尝试或 2 周数据后校准。
- R3 的 72 小时需在 Q-004、Q-005 确认后重算。
- 耗时同时记录中位数和 P90。
- 失败原因分为模型、工具、数据、流程、资源、需求和外部依赖。

## 7. Q-002 决策记录

### 7.1 三维验收

- 功能正确性：流程、数据、权限和异常处理。
- 易用性：理解成本、操作步骤、耗时、误操作、求助和错误恢复。
- 设计合理性：信息架构、心智模型、流程、反馈、一致性、视觉层级、可访问性和信任感。

人格至少覆盖新手目标用户、熟练目标用户、受限或边界用户。发现分为 FunctionalFinding、UsabilityFinding、DesignFinding 和 AccessibilityFinding，必须附操作证据。

### 7.2 初始门槛

| 指标 | 门槛 |
|---|---:|
| 验收证据完整率 | 100% |
| 关键场景通过率 | 100% |
| 总体场景通过率 | ≥80% |
| 未关闭 P0/P1 | 0 |
| 完成核心目标的人格数 | 至少 2/3；只有 2 人格时须全部完成 |
| 无效步骤率 | ≤10% |
| 误操作 | 每任务平均 ≤1 次 |
| 非计划求助 | 每任务平均 ≤1 次 |
| 错误自行恢复率 | ≥80% |
| 设计评分 | 平均 ≥4，且无维度低于 3 |
| 关键可访问性检查 | 100% |
| 可遗留 P2 | ≤3，且不影响核心流程 |

三个画像在同一关键环节全部失败视为 P0。环境故障单独记录，不能算产品成功或失败。

### 7.3 复测规则

- 首轮验收后最多再进行 2 轮复测。
- 每轮复测所有失败场景，并回归全部关键场景。
- 必须展示已修复、仍失败和新增回归。
- 不能降低标准、删除失败场景或修改人格来通过。
- 连续两轮复测不达标，项目进入终止或重新规划。
- AI 人格验收不能替代真实用户验证。

### 8.1 目标与样本

- 安全、隐私、审计和未经复核的高影响动作实行零容忍。
- 质量指标设高门槛，效率指标首月建立基线，贡献指标不设数量 quota。
- 员工单周期至少 5 个完成任务或 2 周数据，否则标记样本不足。
- 高影响绩效动作至少参考 4 周趋势和独立证据。
- 不按消息数、评论数、提案数、代码行数或缺陷发现数量奖励产量。

### 8.2 任务加权

```text
Weight = 1 | 2 | 3 | 5 | 8
```

复杂度由技术不确定性、需求歧义、影响范围、风险、协作和环境难度评分。权重在任务 Ready 前锁定，员工不能自评；拆分任务不得增加总权重。

```text
WeightedScore = TaskWeight × QualityFactor × CapabilityFitFactor
```

质量系数为 1.0、0.8、0.5 或 0；能力系数最高 1.1。单个任务最多占周期加权总量 30%。

### 8.3 多维能力评分

```text
EffectiveCapability =
  40% 模型维度评分
+ 35% 历史任务表现
+ 15% 工具链适配
+ 10% 上下文与技能适配
```

能力维度包括编码、调试、测试、架构、系统设计、产品分析、调研、体验评审、写作、工具使用、长上下文、指令遵循和安全。

认领评分：

```text
ClaimScore =
  40% 能力匹配
+ 20% 历史同类成功率
+ 10% 工具链匹配
+ 10% 成本效率
+ 10% 可用容量
+ 10% 独立性与冲突检查
```

高能力员工优先认领高难度任务，但受 WIP、负载和稀缺能力保护约束。具体负载与改派算法仍在 Q-011。

## 9. Q-004 决策记录

### 9.1 范围

- 里程碑 A“公司成立”：主控自主建岗、规划组织并产出带证据的产品简报。
- MVP“自主交付”：单租户、自托管可运行，从 Charter 到独立验收通过的发布候选完整闭环。

### 9.2 MVP 必须包含

租户与章程、ControlPlane、AI Gateway、Runner、Tool 体系、动态组织、项目管理、沙箱与存储、通信路由、交付质量、发布回滚、治理审计、最小仪表盘、基础记忆和 KPI 复核。

### 9.3 MVP 明确不做

在线支付与计费、完整运营平台、多租户商业化、一键安装包、高级图谱、自动招聘评分平台、自动绩效处罚、技能市场、企业 SSO 和完整 Butler 报告。

- 关键场景 100% 通过，P0/P1 清零。
- 发布失败可回滚，Runner 崩溃不丢任务、成果和账本。
- 模型调用有预算预留和计量，硬预算、租户隔离和密钥边界测试通过。
- 备份可实际恢复，关键决策、成本和组织变更可审计。
- Boss 只处理升级事项，失败项目能复盘并沉淀经验。

## 11. Q-006 决策记录

### 11.1 四层上下文

- 系统与岗位上下文：安全规则、Charter、岗位边界、Tool Profile 和审批状态。
- 任务检查点：目标、计划、当前步骤、决策、风险、失败、Artifact 和下一步。
- 当前工作上下文：最近对话、工具结果、文件片段和评审意见。
- 长期记忆：按租户、岗位、项目和权限检索，带来源和置信度。

### 11.2 压缩与工具输出

- 输入预算达到 70% 时准备压缩；输出预留 20%，安全余量 5%。
- 压缩必须保留目标、约束、决策、失败、反证、证据和下一步。
- 摘要带 `derived_from`，不替代原始事件和 Artifact。
- 超长工具结果写入 RustFS，模型只接收摘要、关键片段和引用。
- 压缩失败时暂停任务，不随意截断。

### 11.3 稳定前缀缓存

上下文按稳定到动态排序：

```text
系统安全规则 → Charter/岗位章程 → Tool Schema
→ TaskCheckpoint → 最近追加对话 → 检索/工具动态片段
```

- 稳定前缀不得插入时间戳、随机 ID 或动态检索内容。
- Tool Schema 保持稳定顺序；Tool Profile 变化才使相关缓存失效。
- 对话采用追加方式，不重写已缓存历史。
- 跨任务只复用稳定前缀，不复用任务检查点和私有对话。
- Charter、岗位、权限或安全策略变化时主动失效。
- OpenAI 与 Anthropic 各自按原生缓存语义计量，不做协议转换。
- 缓存命中不得绕过鉴权或跨租户复用私有内容。

### 11.4 审计与指标

`ContextPacket` 记录检查点、系统和工具版本、引用、排除项、token、压缩原因和缓存信息。初始目标：稳定前缀命中率 ≥90%，可缓存输入 token 命中率 ≥60%；同时监控缓存写入成本、延迟和命中收益。

## 12. Q-007 决策记录

### 12.1 三类版本资产

- PositionCharterVersion：岗位职责、边界、工作方式和技能引用。

- 个人技能通过 ImprovementProposal、评测、审查和试点后发布为组织资产。
- 公共技能保留作者、来源、评测和版本，安装不自动授予权限。
- 跨租户平台资产需要脱敏、匿名化、许可证和平台审核，后置实现。

### 12.4 发布与缓存

- 提示词和技能升级必须经过功能、安全、成本、延迟和缓存回归。

- 审计作者、差异、理由、审批、评测、影响范围和回滚。

## 13. Q-008 决策记录

### 13.1 有界片段与持续工作

- 单次执行片段默认最多 20 个模型轮次、40 次 Tool 调用、3 次连续失败、3 轮无进展。
- 片段到达软限制后保存 TaskCheckpoint、释放租约并立即续跑；限制不终止整个任务。
- 无进展时重新规划、拆分、内部求助或升级，不无限重复。
- 取消后不发起新调用；在途外部写入必须核对结果。

### 13.2 重复与部分成功

- 调用指纹由工具、规范化参数和资源版本组成；重复两次后拦截第三次。
- 相同幂等键返回首次结果；A→B→A 循环也被检测。
- 部分成功先保存成功结果，再只重试失败且幂等的部分。
- 无法确认结果时标记 `OutcomeUnknown`。

### 13.3 成本预警与评审

- 去掉任务级成本硬上限；50% 记录预警，80% 通知直接 Leader，100% 暂停并评审。
- 模型和推理强度绑定员工，任务中不可临时更换。
- 预警沿管理链逐级上报：直接 Leader → 更高层 Leader → Controller → Boss。
- 合理则放行；不匹配则调岗、拆分或调整绑定；内部无法解决才由 Boss 决定。
- 公司 Charter 全局硬预算、安全红线和租户隔离仍保留。

## 14. Q-009 决策记录

### 14.1 聊天与消息

- 支持私人会话、项目群、岗位群、主题群和线程回复。
- 消息类型包括聊天、任务、委派、求助、交接、评审、决策、打断、状态和确认。
- P0/P1 可唤醒员工，普通消息进入队列或摘要。
- `@` 只是定向通知和路由，不自动派工或绕过 CommunicationProfile。
- Ack 表示收到，不表示同意或完成。

### 14.2 委派、交接与提升

- 委派者保留责任，接收者可按能力、负载、上下文或冲突拒绝。
- 交接包含 TaskCheckpoint、Artifact、Decision、风险、失败和下一步，确认后原子转移所有权。
- 聊天线索可提升为 Task、Requirement、Defect 或 Decision；聊天本身不改变状态。

### 14.3 加权召回与渐进披露

- 聊天是弱证据：正式决策 1.0，提升聊天 0.7，项目群 0.4，私人聊天 0.3，未验证传言 0.1。
- 召回按权限、相关度、时间、作者和验证程度加权。
- 披露顺序为通知 → 线程摘要 → 相关消息 → 完整线程。
- 私人会话仅参与者可召回，群聊按范围隔离；摘要和展开再次鉴权。
- 不按消息数、@ 次数或评论数奖励产量。

## 15. Q-010 决策记录

### 15.1 拆分模型

- LLM 生成 DecompositionPlan，控制面校验验收覆盖、依赖、能力、权重、风险和独立性。
- 一个 Task 一个主责、一个可验证结果；初始估算 0.5～1 人日，超过 2 人日继续拆分。
- 单需求默认 3～12 个 Task，超过 12 个拆成子需求。
- 测试、评审、文档和迁移等独立工作必须显式建 Task。
- 子任务总权重不得超过原需求；新增范围必须单独审批。

### 15.2 审批

- 低风险且全部校验通过可自动批准。
- 跨团队、高权重、歧义、新能力、安全、数据迁移或发布风险必须审批。
- 高风险沿管理链逐级审批：直接 Leader → 更高层 Leader → Controller → Boss。
- 提交人不能自审；专业问题可指定评审，但最终管理审批仍沿管理链。
- 自动拆分不等于自动派工，Approved 后 Task 才进入 Ready。

### 15.3 版本与重规划

- 方案状态为 Draft → Proposed → Approved → Active → Revised。
- Approved 冻结；重拆生成增量方案并保留旧 Task、权重和证据。

## 16. Q-011 决策记录

### 16.1 加权 WIP

- 员工容量为 3、5 或 8，由岗位和验证能力决定。
- 当前负载为所有 Claimed、InProgress、InReview Task 的固定权重之和。
- Task 完成前不释放权重，不能靠更新剩余工作量刷容量。
- 同时 InProgress 最多 2 个，高权重任务最多 1 个，预留 20% 容量处理 P0/P1。

### 16.2 认领与公平

- 认领邀请初始有效期 15 分钟，超时或拒绝后推荐下一候选人。
- EffectiveClaimScore 在能力评分上增加负载惩罚、稀缺能力奖励、公平性奖励和连续高负载惩罚。
- 强能力员工优先高难度任务，但连续 3 个周期承担超过 60% 高权重任务时触发复核。
- stretch task 默认不超过员工任务的 20%，但不能突破能力和权限门槛。

### 16.3 改派

- 冻结、离职、调岗、无进展、能力不匹配、截止风险、长期阻塞、负载失衡或成本评审均可触发。
- 顺序为保留并配对 → 拆分 → 改派 → 沿管理链升级。
- 改派由直接 Leader 审批并记录原因，不静默转移。

## 17. Q-012 决策记录

### 17.1 评审 quorum 与证据

- 低风险 1 名非作者；标准 1 名对应能力评审；高权重或核心架构 2 名独立评审且至少 1 名专家。
- 安全、数据迁移和发布需专业评审 + 管理审批；独立验收必须与实现者分离。
- 所有必需评审通过且无阻断项才 Approved；任一要求修改则 ChangesRequested。
- Finding 必须包含级别、类别、证据、影响、建议和是否阻断。

### 17.2 时间盒

- Ack 30 分钟，普通评审 4 小时，高风险 1 个工作日。
- Debate 证据收集 24 小时，证据截止后 4 小时裁决。
- 超时不同意：普通评审改派，争议裁决，高风险升级直接 Leader。

### 17.3 裁决

- 技术评审判断质量，管理裁决决定风险与资源。
- 裁决沿直接 Leader → 更高层 Leader → Controller → Boss。
- 裁决者不能是作者，专家意见不替代最终管理审批。
- Decision 保留理由、证据、条件、反方和复查时间。
- 安全、租户隔离和红线不可被裁决推翻。

## 18. Q-013 决策记录

### 18.1 绑定与路由

- 模型、模型版本和推理强度通过 EmployeeRuntimeBinding 与员工绑定，TaskRun 固定。
- 路由发生在任务分配前，检查能力、上下文、工具、成本、隐私和协议。
- 任务执行中禁止自动跨模型、跨版本、跨推理强度或跨协议切换。

### 18.2 同模型恢复

- 连接失败、429、5xx 允许同模型有界重试。
- 流式中断结算用量并保存检查点，不自动重放工具调用。
- 上下文超限通过压缩、拆分或暂停处理，不换模型。
- 仅允许相同模型版本、推理强度和协议的端点或区域切换。

### 18.3 不可用上报

- 算法连续 2 次失败或 5 分钟持续不可用后生成 ModelUnavailableEvent。
- 事件上报直接 Leader，不主动直达 Controller。
- Leader 决定等待、调岗或调整绑定；绑定调整只影响后续任务。
- 没有直接 Leader 时 Controller 兜底，管理链无法解决才到 Boss。

### 18.4 员工运行状态与 KPI

- 底层状态包括 Active、Busy、Sleeping、RateLimited、Degraded、Unavailable、PendingReview、Frozen、Terminated。
- 界面可拟人显示“生病、疲惫、忙碌、休息”，日志和审计保留真实原因。
- 状态由 Gateway、ControlPlane 和 Sentinel 算法维护，LLM 不得自行修改。
- 可用率、疲惫率、故障率、恢复时间和反复异常次数进入 KPI。
- 必须区分员工、平台/模型和管理原因；只有员工相关且可避免的问题进入员工绩效。
- 反复异常先复核 WIP、任务、工具和模型绑定，不自动触发处罚。

## 19. Q-014 决策记录

### 19.1 models.dev 每日同步

- 每日下载 `https://models.dev/api.json`，校验后生成不可变目录快照。
- 保存来源、获取时间、原始 checksum 和发布版本。
- 对比变更后原子发布；同步失败保留最近有效快照并标记 Stale。
- OpenAI 与 Anthropic 仍使用各自原生协议，目录不承担协议转换。

### 19.2 BYOK 预填与补价

- BYOK 从 models.dev 预填模型、限制、能力和已有价格。
- models.dev 缺失的价格字段由用户填写，必须包含币种、单位、区域和生效时间。
- 仍然缺失的价格标记为未定价，不得按 0 计算。
- 每日同步按 Provider + Model ID 精确匹配；models.dev 新增字段自动覆盖对应手工字段。
- 覆盖只影响后续请求，历史 usage 和账目不改写，并通知 BYOK 管理员。

### 19.3 价格结算

- 每日消耗按请求发生时的有效价格快照计算。
- 有效价格由 models.dev 字段和用户补充字段合并而成。
- 输入、输出、缓存读写和长上下文阶梯价格分别记账。
- 价格缺失或目录过期时进入对账与告警，不静默猜测。

### 19.4 自动档位

- 不手工维护 cheap/mid/premium 模型清单。
- 档位由 models.dev 的价格、上下文、推理、工具、结构化输出、模态和知识数据计算。
- 算法和结果版本化；缺失数据标记 Unclassified。
- 档位只用于筛选、招聘和预算策略，不替代精确模型绑定。
- 目录变化只影响新任务，不自动换模型或调岗。

## 20. Q-015 决策记录

### 20.1 复用与版本

- 评测结果按模型版本、推理强度、PromptBundle、Tool Profile、Runtime、数据集、评分策略和 seed 建立缓存键。
- 同一公司内可复用完全匹配的结果，新岗位只运行补充集。
- 跨租户默认不共享，公共评测必须匿名、脱敏并审核许可证。
- 已发布数据集、评分和结果不可静默修改。

### 20.2 数据与防泄漏

- BenchmarkSuite、DatasetVersion、BenchmarkCase 和评分规则版本化并记录来源、hash、许可证和脱敏状态。
- 密封集不向员工、模型和普通管理界面开放。
- 评测用例不进入生产记忆、Skill 或 Prompt。
- 公开数据集增加污染、近似重复和 canary 检查。

### 20.3 频率与门槛

- 新模型运行完整核心集，每日 canary、每周核心回归、每月全量，Prompt/Skill/Tool 变化运行受影响集合。
- 安全、租户隔离和越权案例 100% 通过，P0/P1 为 0，核心案例 100%，整体 ≥80%，单维度 ≥70%。
- 连续运行 3 次并报告波动；关键指标下降不超过 5 个百分点，单维度不超过 10 个百分点。
- 延迟和成本必须符合岗位预算。

### 20.4 评分与使用

- 确定性测试优先，规则评分其次，LLM Judge 和人工抽检补充。
- Judge 版本固定、独立于被评模型，并记录与人工的一致性。
- 评测通过不自动绑定员工；失败不自动触发处罚。
- 招聘、技能公共化、调岗和模型升级引用评测版本。

## 21. Q-016 决策记录

### 21.1 存储布局

- 生产关系数据统一使用 Postgres；SQLite 仅用于单租户开发和测试。
- 二进制快照、成果、报告和数据集统一使用 RustFS，直接使用 S3 SDK，不保留 ArtifactStore 多实现抽象。
- 活动 Git 工作区使用 Runner 本地目录或容器隔离目录，属于临时计算空间。
- Postgres 保存工作区版本、Git 引用、checksum 和 RustFS 对象引用。

### 21.2 Schema 与租户隔离

- 按领域划分 Schema，但仍在同一个数据库；Schema 不是租户隔离边界。
- 租户业务表采用共享表 + tenant_id + 强制 Postgres RLS。
- 应用角色不是表 Owner、没有 BYPASSRLS；事务使用 SET LOCAL app.tenant_id。
- 租户主键、唯一约束、外键和索引包含 tenant_id；迁移角色与运行角色分离。

### 21.3 事务与一致性

- 单库短事务维护认领、编制、预算、结算、消息和评审等即时不变量。
- 跨模块使用 Outbox、Inbox 和 Saga，不采用 XA/2PC 或跨服务长事务。
- 默认 Read Committed；队列使用 SKIP LOCKED，预算和编制按需行锁或 Serializable 重试。
- RustFS 上传使用 PendingUpload → Ready 状态机，Ready 对象不可覆盖。

### 21.4 状态类型

- 数据库状态使用稳定的小写 snake_case 字符串。
- 代码使用密封引用类型包装，禁止业务代码传播裸状态字符串。
- EF Core 配置双向 ValueConverter，JSON 对外仍序列化为字符串，数据库 CHECK 约束兜底。

### 21.5 分区与验证

- MVP 不预先分区；超过约 1000 万行/月、500GB 或已影响 SLO 时按月分区高增长表。
- 优先分区 llm_usage、ledger_entries、audit_events 和 messages。
- RLS、并发预算、任务认领、编制、Outbox 崩溃恢复和 RustFS 一致性必须使用 Postgres 集成测试验证。

## 22. Q-017 决策记录

### 22.1 部署与版本集

- MVP 和自托管采用单机 Docker Compose + systemd 监管，Postgres、RustFS、四个服务和两个前端同机部署。
- 每次发布生成 ReleaseManifest，固定镜像 digest、schema、API、事件和兼容版本。
- 四个部分作为版本集发布，升级期间只允许 N/N-1 混跑，N-2 Runner 拒绝注册。

### 22.2 升级顺序

1. Drain 新任务和模型调用，等待在途工作到安全点。
2. 备份并验证 Postgres、RustFS 和密钥库。
3. 执行 Expand Migration。
4. 依次部署 ControlPlane、Gateway、Runner、TenantDashboard、Operations。
5. 执行健康检查和 smoke test。
6. 恢复业务并观察。
7. 所有实例升级后在后续发布执行 Contract。

### 22.3 迁移与回滚

- 生产禁止启动时自动迁移；独立 Migration Job 使用迁移角色和 advisory lock。
- Expand 只做兼容变更，破坏性变更至少延后一个版本。
- 大表回填分批、限速、可恢复并记录校验和。
- 应用仅在 Expand 且数据兼容时回滚；已 Contract 或数据不兼容时必须前滚或恢复备份。
- 数据库不自动回滚，恢复备份必须明确 RPO/RTO。

### 22.4 混版本与配置

- API 和事件向后兼容，消费者忽略未知字段并拒绝不支持的主版本。
- Runner 声明最低控制面版本，旧 Runner 只完成已认领任务。
- 配置具有 schema 版本并前置校验；旧版本忽略未知键以避免阻塞回滚。
- 密钥不写入镜像和普通配置。

## 23. Q-018 决策记录

### 23.1 可观测性后端

- 四个服务和两个前端统一使用 OpenTelemetry 采集指标、日志和追踪。

- 日志使用结构化 JSON，并带 trace_id、span_id、tenant_id、task_id 和原因码。

- 正常追踪默认采样 10%，错误、L2/L3、预算、越权和关键发布路径 100% 保留。

- 沿用控制面可用性 99.5%、任务领取 P95 2 秒、消息 P95 10 秒、用量入账 P95 60 秒等目标。
- 增加 Outbox 投递、RustFS 上传和任务认领成功率目标。

- L2 路由直接 Leader/值班负责人，L3 通知 Controller 和 Boss。

### 23.4 测试基线

- 单元测试使用 xUnit，集成测试使用真实 Postgres 和 RustFS。
- Provider 使用原生契约测试，CI 不依赖真实 Provider。
- E2E 覆盖完整交付闭环，UI 使用 Playwright for .NET。
- 整体覆盖率 ≥80%，安全、预算、账本、RLS 和状态机 ≥90%。
- MVP 容量基线为 20 员工、40 并行任务、100 任务/小时、1000 消息/小时。
- 故障、混沌、安全、升级和恢复测试进入发布门禁。

### 23.5 可插拔 Profile

- OpenTelemetry SDK 默认接入，后端支持 `off`、`local`、`otlp`、`elastic` 四种 Profile。
- 自托管默认 `local`，只写 stdout/journald 或轮转日志，不启动额外遥测容器。
- `otlp` 发送到用户已有后端；`elastic` 才启动 Elasticsearch、Kibana、APM Server 和 Collector。
- Elastic 组件放入可选 Compose Profile，默认不启动。
- 指标、日志和追踪可独立开关；Profile 修改后重启生效。
- 遥测健康不进入核心 Ready 检查，后端故障不阻塞业务。

## 24. Q-019 决策记录

### 24.1 信任与隔离

- 外部网页、Issue、代码、文档、消息、Tool/MCP 输出、记忆片段和其他员工内容均标记为不可信数据。
- 内容使用 UntrustedContent 信封保存来源、hash、租户、任务、taint 和风险信息。
- 系统规则、Charter 和 Tool Schema 保持在可信前缀，外部内容进入独立数据段。
- 摘要、压缩、检索和记忆提升不得洗白 taint。

### 24.2 TaskGrant 自主空间

- 任务创建时预授权工作区、Tool、网络、预算、WIP 和动作范围。
- Grant 内不逐步审批、不主动上报 Controller，员工可以自主试错和恢复。
- 只有突破 Grant、权限、预算或红线时才暂停并沿管理链升级。
- 不可信内容不能激活 Tool、扩大 Capability、修改模型/预算/编制或伪造审批。

### 24.3 检测与处置

- 确定性检测优先，模型检测只作辅助，不能仅凭分类器授权。
- 默认按 Allowed、Sanitized、Quarantined、RequiresReview、Blocked 分级。
- 可疑内容默认标记、清理并继续安全分析，不因误报中断整个任务。
- 高风险动作暂停必须绑定 action_hash、参数、资源、审批人和有效期。
- 被隔离来源不处罚员工，员工可换来源继续。

### 24.4 审计与指标

- 记录内容来源、hash、检测器版本、发现、处置、后续 Tool Call 和审批引用。
- 原始敏感内容不进入普通日志。
- 统计无审批完成率、不必要中断率、安全边界内自主完成率、误报中断和跨任务 taint 传播。
- 注入误报导致的任务中断目标为 0，权限提升、跨租户和未审批高风险动作保持零容忍。

## 25. Q-020 决策记录

### 25.1 Claim 与检测

- 记忆拆分为 MemoryClaim，每个 claim 独立保存来源、证据、置信度、验证、taint、冲突和引用。
- 检测来源可信度、证据缺失、同源重复、冲突、异常灌入、摘要提升置信度和已知攻击模式。
- 重复出现不等于独立验证，必须记录来源多样性。

### 25.2 隔离与纠错

- 状态支持 Active、Disputed、Quarantined、Corrected、Superseded、Stale、Archived、Purged。
- 高风险 claim 立即停止召回，低风险降权复核。
- CorrectionTask 是可认领、加权、验收的正式任务，复核者与作者/来源提交者分离。
- 纠错生成新版本并引用旧 claim，不静默修改原文。
- 隔离必须有理由、期限和复核，支持反证申诉。

### 25.3 影响与传播

- MemoryImpactRecord 记录哪些员工、任务、摘要、决策和外部动作引用过受影响版本。
- 在途任务标记上下文失效并重新检索，高风险动作暂停。
- 已完成任务按状态创建 Defect、ReviewTask 或回归任务，不自动回滚。
- 纠正通过 Outbox 传播到向量、全文、图、缓存、派生摘要和通知。
- 只处理受影响 claim 和引用链，不关闭整个记忆系统。

### 25.4 通知与指标

- 先通知直接负责人，再沿管理链升级；跨公司或红线进入 Controller/Boss。
- 统计检测时间、召回暴露、纠错时长、传播延迟、遗漏任务、误隔离和重复投毒。
- 员工主动报告投毒不扣 KPI。

## 26. Q-021 决策记录

### 26.1 不可变制品

- Tool、MCP Server、Skill Package、NuGet 依赖、容器镜像和安装包统一登记为 SupplyChainArtifact。
- 制品按版本和 digest 固定，保存签名、来源、许可证、SBOM、扫描和审批记录。
- 生产禁止 latest；NuGet 使用签名和 lock file，自托管支持离线签名验证。

### 26.2 准入门禁

- 流程为签名验证 → digest 固定 → SBOM → 漏洞扫描 → 许可证 → 权限/网络审查 → 隔离试运行 → 审批。

- MCP 新增 Tool 默认禁用；Skill 不能自行授予 Capability 或 Tool。

### 26.3 运行与更新

- TaskRun 固定 Tool、MCP、Skill 和镜像版本，不中途升级。
- 已批准制品可自主调用，不需要每次审批；安装、升级、扩权或突破沙箱才审核。
- 新版本先 canary、回归和安全复核，回滚恢复旧 digest。
- 运行层仍执行 Capability、Tool Profile、TaskGrant 和 PEP 校验。

### 26.4 撤销与指标

- 恶意或漏洞制品禁止新任务加载，按 digest 查询影响、暂停高风险动作并轮换可能暴露的凭据。
- 不删除历史证据，不处罚使用已批准制品的员工。
- 统计签名/SBOM 覆盖率、未批准调用、Critical 漏洞、撤销传播时间和影响任务数。

## 27. Q-022 决策记录

### 27.1 分类与检测

- 数据分为 Public、Internal、Confidential、Restricted；秘密和敏感 PII 默认 Restricted。
- 在 API、聊天、Tool、模型出站、记忆、Artifact、日志、Trace、导出和通知边界执行 DLP。
- 检测密钥格式、私钥、连接串、PII、高熵、编码拆分和 OCR 内容。

### 27.2 处置

- 秘密只存在于密钥系统，业务系统只保存 secret_ref；高置信秘密立即阻止并触发轮换评估。
- PII 默认遮蔽、令牌化、假名化或匿名化；模型上下文只发送必要字段。
- 租户可配置 PII 政策，但不能关闭秘密保护。
- 审计只保存规则、字段类型、对象、动作和哈希，不保存秘密或完整 PII。

### 27.3 存储与删除

- Restricted 字段和 RustFS 对象加密，对象键和索引不包含 PII。
- 向量、全文、图、缓存和派生摘要只存脱敏内容。
- 删除通过影响图传播到 Postgres、RustFS、索引、缓存、遥测副本和令牌映射。
- 法律保留期间禁止清除，备份按保留期到期处理并输出删除证明。

### 27.4 误报与指标

- 高置信秘密默认阻止；PII 误报默认遮蔽并允许继续安全任务。
- 例外必须绑定字段、范围、原因、负责人和到期时间，员工不能自行关闭 DLP。
- 秘密泄漏和未脱敏 PII 进入模型目标为 0；统计覆盖率、误报、轮换和删除传播时间。

## 28. Q-023 决策记录

### 28.1 完整性 Profile

- 默认 standard：追加写、租户/流级哈希链和每日签名 Merkle 检查点。
- worm：standard + RustFS Object Lock 或法定保留。
- anchored：worm + 外部独立 root 锚定，默认不强制外部服务。

### 28.2 事件与检查点

- 业务状态与审计事件通过同一事务 Outbox 提交。
- 审计角色只有 INSERT/SELECT，更正通过新事件引用旧事件。
- event_hash 使用规范化载荷和 prev_hash，seq 连续并可检测缺口。
- 检查点包含范围、Merkle root、签名密钥 ID 和签名，写入版本化 RustFS。
- 审计不保存秘密和完整 PII。

### 28.3 验证与锚定

- 验证器重算事件链、seq、Merkle root、签名和对象保留状态。
- HashMismatch、GapDetected、SignatureInvalid 等进入安全事件，不静默修复。
- 外部锚定只发布 root、范围、时间和签名，不发布业务内容。
- 锚定失败进入告警和补发；合规 Profile 可阻止高影响动作。
- 单机无法抵抗 DB、签名密钥和锚点同时被控制，权限与密钥分离是必要条件。

### 28.4 指标

- 链验证成功率、seq 缺口、检查点和锚定滞后、签名失败、WORM 违规尝试、篡改事件和验证覆盖率。

## 29. Q-024 决策记录

### 29.1 工号与任职周期

- 每个员工拥有全局唯一、不可变、永不复用的 employee_no。
- 调岗保留工号和员工运行时，在同一事务结束旧任职并创建新任职。

- 主控可以决定不录用候选人，但录用、再入职和移除订阅必须由 Boss 最终批准。
- 主控不能通过停唤醒、不续签或零预算变相移除员工。

- 公司成果、任职历史、审计和组织资产保留。
- 项目共享内容交接给指定接收人；个人记忆、私人聊天和私有草稿默认隔离。
- 秘密吊销或轮换，不转移、不继承。
- 离职生成 OffboardingHandoff，未提交改动先扫描再快照和交接。

### 29.4 移除订阅

- Boss 决定后停止新任务、撤销全部访问、移除员工运行/模型订阅并释放编制。
- 主控无继任者时不能移除。
- 申诉窗口未完成时暂停执行。
- 再入职使用原工号但不恢复旧凭据，组织成果仍关联历史身份。

### 30.1 范围与分级

- 处置支持 Allow、AllowWithLabel、Sanitize、RequiresReview、Block、Quarantine、Escalate。
- 默认只阻止违规内容或动作，不冻结员工全部工作。
- 对外发布、公共仓库和外部 API 输出必须通过内容安全门禁。
- 内容安全通过不替代发布审批。

### 30.3 申诉与证据

- 误报可申诉，复核者独立，例外必须绑定范围、负责人和到期时间。
- 员工主动报告风险不扣 KPI，误报进入规则校准。
- 普通审计只保存 hash、类别、策略/检测器版本、风险和动作。
- 法律取证单独加密、最小权限并记录访问。

### 30.4 合规与指标

- 合规政策按地区、行业和客户要求版本化，遵守 Provider 政策、数据驻留和年龄限制。
- 自托管可提高保护，但不能关闭平台红线。
- 统计精确率、召回率、误报、申诉推翻、复核时长、红线逃逸和正常任务不必要阻断。

## 31. Q-026 决策记录

### 31.1 等级与角色

- 安全事件分为 SEV1～SEV4；SEV1 包括正在发生的跨租户泄漏、密钥失控和审计篡改。
- 事件由 Incident Commander 负责，技术、取证、沟通和记录角色按能力分配。
- 主控不能压下事件或自行宣布恢复。

### 31.2 遏制与取证

- 可自动撤销会话、冻结 Runner/Tool/制品、阻断域名、隔离容器和暂停任务。
- 删除数据、关闭租户、对外声明和联系监管等动作仍需审批。
- 证据包括审计链、日志、Trace、快照、镜像/制品 digest 和影响清单。
- 证据加密、哈希、WORM 和全程访问审计，普通聊天不粘贴秘密和完整 PII。

### 31.3 通知与恢复

- SEV1 立即通知 Boss、IC 和受影响租户；状态页只发布脱敏影响。
- 外部通知只写已知事实、影响、措施和下次更新时间。
- 恢复需根因控制、凭据轮换、干净版本、对账、监控和 IC 批准；SEV1 还需租户/Boss 确认。

### 31.4 复盘与指标

- 复盘记录时间线、根因、控制有效性、影响、响应耗时和改进任务。
- 默认无责归因员工个人，故意滥用另行处理。
- 统计 MTTD、MTTA、MTTC、MTTR、通知延迟、证据完整率、复发率和行动完成率。

## 32. Q-051 决策记录

- 管理链由组织树生成，负责资源、绩效和审批。
- 专业链由岗位标签和能力生成，负责技术、产品、质量和运营问题。
- 专业路由沿祖先查找目标标签，可跳过没有目标标签的管理岗位。
- 跨分支需要 CommunicationGrant 或项目覆盖，跨租户始终禁止。
- 通信只扩大可联系对象，不扩大 Tool、预算、组织或审批权限。
- 路由绑定组织版本；标签、岗位或项目关系变化后旧路由失效。
- 所有穿透、拒绝、改派和撤销均审计，详见 [12 通信与穿透路由](./design/12-communication-and-routing.md)。
