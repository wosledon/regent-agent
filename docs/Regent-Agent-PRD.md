# Regent-Agent（摄政）—— 产品需求文档（PRD）

- 版本：v0.1（草案）
- 日期：2026-11-22
- 状态：待产品评审
- 产品名称：**Regent-Agent**（摄政）
- 产品定位：人类编写公司章程，平台运营一家能够自主发现市场、组建组织、开发产品并完成独立验收的软件公司。

> 本文定义产品的目标、范围、用户需求、业务规则和验收标准，不描述具体技术实现。架构、接口、数据、安全与部署设计见 [技术设计文档](./Regent-Agent-技术设计.md)。

---

## 1. 背景与问题

传统 AI 助手需要人类持续拆解任务、协调角色、检查结果和推进项目，无法承担一个完整业务闭环。

Regent-Agent 要解决的是：

1. 如何把人类的高层意图转化为可持续执行的公司目标。
2. 如何让组织自主招聘、分工、考核和调整，而不是依赖人工编排。
3. 如何确保开发成果有证据、有验收，而不是只生成看似合理的代码或报告。
4. 如何让人类保留最终治理权，同时不必参与日常执行。
5. 如何在多租户、BYOK 和开源部署下隔离数据、密钥、预算与责任。

## 2. 产品愿景与定位

Regent-Agent 不是聊天工具，也不是固定工作流脚本，而是一个**公司孵化与运营平台**。

- 股东提交一份长期有效的公司章程。
- 公司从市场调研开始，自主形成第一个产品简报。
- 组织根据产品需要自行招聘、面试、分工、考核与调整。
- 产品必须经过独立“模拟真实用户”的体验验收。
- 项目可以失败，但公司使命持续，失败经验进入公司记忆。
- 人类通过管家、仪表盘和升级队列观察与治理，不介入日常执行。

产品采用多租户 SaaS 形态，同时支持源码全套自托管。每个租户拥有自己的章程、组织、模型池、预算、数据和公司。

### 2.1 产品四部分

| 部分 | 服务对象 | 核心职责 |
|---|---|---|
| 控制面（ControlPlane） | 租户 | 公司运行、组织、任务、消息、账本、管家和租户仪表盘 |
| AI 网关（AI Gateway） | 控制面与 Runner | 模型密钥、原生协议代理、路由、预算和计量 |
| Runner | 平台运行时 | 主控与员工计算、沙箱、工具执行和资源上报 |
| 运营平台（Operations Platform） | 提供方 | 租户账户、套餐、资源池、事件、计费、备份、支持访问和运营审计 |

租户控制面与运营平台分开鉴权、分开界面、分开审计。运营平台默认不能读取租户业务内容和模型密钥。

## 3. 目标用户与角色

| 角色 | 核心诉求 | 主要操作 |
|---|---|---|
| Boss / 老板（Owner） | 用少量输入获得可验证的业务结果 | 编写章程、配置模型与预算、处理升级、观察公司 |
| 管家（Steward） | 把公司状态翻译为股东可理解的信息 | 只读查询、对话解读、报告投递、升级建议 |
| 员工 Agent | 在明确职责和权限内完成工作 | 调研、规划、开发、测试、运维、体验验收 |
| 平台运营方 | 保障托管服务可用、安全、可审计 | 租户管理、容量管理、系统监控、备份与恢复 |

### 3.1 主控与动态组织

公司不预设固定角色谱系。每个公司有一个持续存在的 **主控（Controller）**，它是编排运行时，不是预设的 CEO 岗位。

- 主控启动后根据章程为自己创建岗位，可以选择任意合规名称。
- 主控再根据目标自主创建、合并、拆分和调整其他岗位。
- 岗位名称、职责、能力、模型档位、预算和汇报关系都是数据。
- 权限和调度基于能力，不基于“CEO、HRBP、CTO”等名称。
- 独立验收必须由与实现者不同的员工承担，但岗位名称不固定。
- 管家不是公司员工，不占编制、不参与公司管理决策。
- 平台治理与公司治理是两套不同体系。

### 3.2 核心概念

| 概念 | 性质 | 关键规则 |
|---|---|---|
| Boss / 老板 | 人类租户所有者成员 | 不是 Agent，不占编制；Primary Owner 唯一，Co-Owner 和代理权限显式授予 |
| Controller / 主控 | 唯一的编排 Agent 运行时 | 每家公司一个 Active 主控；启动后为自己创建岗位 |
| Employee Agent / 员工 Agent | 独立业务执行 Agent | 有独立运行时、岗位、能力和上下文；不是主控的内部函数 |
| Agent Context / 智能体上下文 | 系统规则、任务检查点、工作上下文和记忆检索 | 检查点持久化；稳定前缀优先缓存；摘要不替代真相 |
| Prompt Bundle / 提示词包 | 系统提示、岗位 Charter、技能和工具画像的固定版本组合 | TaskRun 固定版本；可评测、可回滚、可审计 |
| Agent Chat / 智能体聊天 | 私人会话、项目群、岗位群和主题线程 | @ 路由、加权召回、渐进披露；聊天不直接改变任务状态 |
| Employee Operational State / 员工运行状态 | Active、Busy、Sleeping、RateLimited、Degraded 等确定性状态 | 算法维护；界面可拟人展示；KPI 必须原因归因 |
| Model Catalog / 模型目录 | models.dev 每日快照、BYOK 补价和自动档位 | 目录版本化；models.dev 优先，历史账目不可改写 |
| Benchmark Suite / 评测集 | 版本化案例、密封集、评分规则和 EvaluationRun | 公司内匹配复用；防泄漏；结果作为能力证据 |
| Data & Object Storage / 数据与对象存储 | Postgres、RustFS 和 Runner 本地隔离工作区 | 状态、快照和活动代码分层；RLS 与事务保证隔离 |
| Release Manifest / 发布清单 | 版本 Tag、基础镜像 digest、本地镜像 ID、schema、API、事件和兼容版本 | 版本集发布；Expand/Deploy/Contract；明确回滚边界 |
| Telemetry Backend / 遥测后端 | OpenTelemetry + off/local/otlp/elastic Profile | 默认 local；Elastic Stack 可选；统一指标、日志和链路追踪 |
| Untrusted Content / 不可信内容 | 外部内容信封、来源、hash、taint 和风险处置 | 不提升权限；taint 跨摘要和记忆保留 |
| Task Grant / 任务授权 | 工作区、Tool、网络、预算和动作范围 | Grant 内完全自主，只有越界才审批 |
| Memory Claim / 记忆声明 | 来源、证据、置信度、taint、冲突和引用 | claim 级隔离、版本化纠错和影响传播 |
| Correction Task / 纠错任务 | 可认领、加权、独立复核的正式任务 | 生成新版本，不静默改写原文 |
| Supply Chain Artifact / 供应链制品 | Tool、MCP、Skill、依赖和镜像的版本/digest/签名/SBOM | 准入审核、版本锁定、按版本撤销和影响分析 |
| Sensitive Data Policy / 敏感数据政策 | Public/Internal/Confidential/Restricted 分类与 DLP | 秘密隔离、PII 令牌化、审计元数据和删除传播 |
| Audit Integrity Profile / 审计完整性 | standard/worm/anchored、哈希链、Merkle 检查点和外部锚定 | 可检测篡改、缺口、签名失败和保留违规 |
| Employee No / 员工工号 | 全局唯一、不可变、永不复用 | 调岗和再入职保持身份连续 |
| Pending Removal / 待驱逐 | 低统一评级的独立复核队列 | 主控提名，Boss 最终决定移除订阅 |
| Content Safety Policy / 内容安全 | 版本化规则、检测器、分级处置和申诉 | 正常内容自动放行，红线阻止，模糊场景复核 |
| Security Incident Response / 安全事件响应 | SEV1～SEV4、IC、遏制、取证、通知、恢复和复盘 | 先控制影响，破坏性动作仍需审批 |
| Account Identity / 账户身份 | 账号密码、GitHub OAuth、一次性恢复码 | 以不可变第三方用户 ID 识别，仅按已验证邮箱自动合并 |
| Enterprise OIDC / 企业单点登录 | 租户 issuer+sub、邀请、组映射、IdP MFA 和紧急恢复 | OIDC 第一梯队，SAML 暂缓 |
| Tenancy & Ownership / 租户与所有权 | 账户多租户、Primary/Co-Owner、限时代理和租户切换 | 一租户一公司，跨租户默认不共享 |
| Soft Deletion / 软删除 | 逻辑删除、加密隔离、限时恢复、物理清除和 tombstone | 删除立即生效，清除按窗口执行 |
| Retention & Archive / 保留与归档 | 保留类、Hot/Archive/Cold、manifest、授权恢复和冷检索 | 归档不改变隔离、审计和删除优先级 |
| Backup Profile / 备份配置 | 可选全量、PITR、对象、密钥、异地和演练开关 | 默认关闭，启用后才计算有效 RPO/RTO |
| Output Rights / 产出权利 | 租户归属、平台有限许可、第三方权利和来源记录 | 归租户但不覆盖第三方许可，不保证版权保护 |
| Fairness Policy / 公平招聘政策 | 岗位相关标准、盲评、分群审计、合理便利和申诉 | 偏差触发调查，不降低能力门槛 |
| Open Source Policy / 开源政策 | Apache-2.0、NOTICE、SBOM、贡献者和商业边界 | 核心开源，商业收入来自服务 |
| Dashboard IA / 仪表盘信息架构 | Boss 首屏、两级导航、项目健康和行动中心 | 只突出健康、风险和待决策事项 |
| Approval Policy / 审批策略 | 缺席协商、分级审批、委托、备用审批人和 SLA | 协商不创造权限，超时仍拒绝 |
| Locale Policy / 本地化策略 | zh-CN/en-US、时区、格式和翻译治理 | UTC 存储，locale 展示，无障碍后置 |
| Work Schedule / 公司作息 | 全天可配置、静默窗口、低价窗口和成本感知调度 | 用户自行设置，安全事件可唤醒 |
| Delivery Pipeline / 交付管线 | GitHub 版本 Tag、Actions 检查和本地 Compose 构建 | 不发布镜像，不引入多平台和多环境系统 |
| Cost Governance / 成本治理 | 直接归属、显式分摊、不自动结转和确定性异常 | 成本只记一次，异常不自动改预算或惩罚员工 |
| Model Runtime / 模型运行边界 | 仅 OpenAI 与 Anthropic 云端原生端点 | 不支持本地 GPU、Ollama 或本地模型 |
| Notification Center / 通知中心 | 仅仪表盘内部通知、持久化和实时推送 | 外部渠道全部后置 |
| Extension Boundary / 扩展边界 | 仅内部 API、Tool 和内部 MCP 工具面 | 公共 API、SDK、Webhook 和市场后置 |
| Self-host Install / 自托管安装 | Tag 源码、Compose、systemd 和简单脚本 | 无二进制安装包、激活或自动更新 |
| Capacity Baseline / 容量基线 | 单机聚合容量、API P95、队列上限和租户公平 | 当前不承诺大规模多租户容量 |
| Compliance Profile / 合规配置 | 地区、Provider/区域、保留、审计、备份和共享策略 | 必需项 fail closed，不宣称认证 |
| Position / 岗位 | 组织树节点与编制槽 | 定义名称、职责、能力、模型、预算和汇报关系；可空缺 |
| PositionAssignment / 任职关系 | 员工与岗位的关系 | 一个员工一个主岗位，一个岗位一个主任职者；调岗保留历史 |
| OrganizationTree / 组织树 | 岗位关系的投影 | 只有一个根岗位、无环、层级不超过 4 |
| OrgManagementGrant / 组织管理授权 | 主控委托的管理权限 | 按子树、动作、预算和期限授权，可撤销、可审计 |
| Position Label / 岗位标签 | 描述职责、专业和通信关系的数据 | 标签不决定权限；技术标签可向上穿透查找祖先岗位 |
| Communication Profile / 通信画像 | 当前员工可联系的对象和路由方式 | 管理链处理权力，专业链处理问题；项目可临时覆盖 |
| Tool / 工具 | LLM 可发现的受控操作 | 权限上限与当前工具画像分离；执行时再次鉴权 |
| Tool Profile / 工具画像 | 当前任务默认披露的工具集合 | Primary 完整披露，Auxiliary 渐进披露，Restricted 需激活或审批 |
| Project / 项目 | 目标、范围、里程碑和成员的管理容器 | 管理者按能力创建；项目可暂停、取消、完成并复盘 |
| Requirement / 需求 | 可评审、拆分和验收的工作意图 | 必须具备验收标准；开发认领从需求拆出的任务 |
| Task Type / 任务类型 | 描述本次工作的语义类别 | 决定能力、工具画像、权重、Done 和 KPI，不绑定岗位名称 |
| Defect / 缺陷 | 测试或验收发现的问题 | 测试提交，开发修复，测试复测关闭 |
| Discussion / 讨论决策 | 围绕工作项的线程、争议和裁决 | 讨论不直接修改状态；结论形成 Decision 并保留反方意见 |
| Workflow / 工作流 | 可版本化的组织流程资产 | 个人草稿可自主使用；组织范围绑定岗位子树，需沿组织树向上的 Leader 审查采纳 |
| Memory / 记忆 | 员工与组织的知识数据 | 个人记忆私有，可沿组织树向上提名；支持 RAG 与有界图谱多跳 |
| Knowledge Base / 知识库 | 已发布的公共知识资产 | 公司根范围共享，来源、版本、置信度和有效期可追踪 |
| Self-Drive / 自驱动 | 员工主动反思和改进的循环 | 所有员工均可提出流程、技能、工具和组织改进，但不能自行扩权 |
| KPI / 绩效指标 | 员工、岗位和公司的可衡量目标 | 数据来自控制面事实，按周期或事件评估 |
| Performance Review / 绩效评估 | 基于证据的评估与决策 | 自评、复核、动作、申诉和审计分离 |
| Human Performance Review / 人类事后审查 | 人类对高影响绩效动作的事后审查 | 可推翻结论和要求纠正，不参与日常事前审批 |
| Sentinel / 哨兵 | 纯程序算法 | 不调用 LLM、不是 Agent、不占编制，只监控和触发预定义动作 |
| Butler / 管家 | 股东只读 LLM 助手 | 不是公司员工，不参与经营决策 |

Boss 的展示名称由 `display_name + title_suffix` 组成，例如 `张三老板`、`Alice Boss`。权限始终来自 Owner 身份，不来自展示后缀。

### 3.3 岗位、任职与组织树

- 岗位是组织节点和编制槽，可以先于员工存在。
- 员工通过任职关系绑定岗位，岗位与员工不直接等同。
- 组织树由岗位的 `reports_to_position_id` 生成，空缺岗位仍保留在树中。
- 主控可以自己管理组织，也可以通过 `OrgManagementGrant` 把指定子树的管理权委托给员工 Agent。
- 委托范围包括可执行动作、预算调整上限和有效期；主控保留最终责任。
- 受委托员工使用与主控相同的组织变更 API，不能绕过编制、预算、层级和审计约束。

### 3.4 Tool 驱动操作

- 主控和员工 Agent 的内部管理、业务操作和跨 Agent 协作统一通过 Tool Call 完成。
- 员工的 Authorized Tools 是权限上限；当前任务的 Tool Profile 决定默认披露哪些工具。
- 高级岗位可以显式继承下级能力，但默认以本岗位主要职责的工具为主。
- Tool 分为 Primary、Auxiliary、Restricted、Forbidden；Primary 完整披露，Auxiliary 渐进披露，Restricted 需激活或审批。
- 普通开发 Agent 不能获得组织管理、预算修改或升级审批权限；架构师可以拥有编码能力，但默认主要披露架构设计和技术选型工具。
- Tool 执行前必须再次校验身份、租户、能力、资源范围、当前激活状态、参数和业务规则。
- Tool 授权和画像变更由控制面管理，支持刷新、撤销、审计和幂等执行。

### 3.5 可复用工作流

- 员工在工作中有意识地归纳流程，形成 Workflow Draft。
- 工作流范围只有个人和组织两种；组织范围绑定当前组织树上的一个岗位子树。
- 员工可以个人使用，也可以沿自己所在岗位的上级路径提名到任意祖先岗位范围，不能跨分支提名。
- 组织级工作流由该范围内具备 `workflow.review` 能力的 Leader 审查；权限不足时继续向上路由。
- Leader 决定采纳、修改、试点或拒绝；公司范围就是根岗位范围，不是额外的固定层级。
- 已采纳版本不可变，改进必须创建新版本。
- WorkflowRun 固定使用一个版本，执行过程通过任务和 Tool 完成。
- 工作流不能提升执行者权限，只能声明所需能力和 Tool。

### 3.6 记忆与知识库

- 员工个人记忆默认私有，主控和其他员工不能直接读取。
- 员工可以将个人记忆沿组织树向上提名为组织记忆或公司知识库资产。
- 组织记忆绑定岗位子树；知识库是公司根范围的公共知识资产。
- 记忆支持情节、语义、程序和反思类型，并保留来源、版本、置信度和有效期。
- 检索采用关键词、向量和元数据混合召回，并可有界扩展知识关系。
- 记忆必须支持衰减、停止召回、归档和彻底删除，删除动作同步清理索引、关系、缓存和派生内容。

### 3.7 自驱动与绩效

- 所有员工都运行“执行 → 反思 → 提案 → 审批 → 改进 → 验证”的自驱动循环。
- KPI 按公司、岗位和员工定义，数据来自任务、成果、成本、质量、工作流和审计。
- 主控默认每 7 天进行一次绩效周期，其他员工周期可配置。
- 主控可以创建 HRBP 或任意考核岗位，但评估权限来自能力，不依赖岗位名称。
- 绩效动作包括保持、辅导、流程优化、模型调整、调岗、降职、冻结和解雇。
- 非解雇动作由 Controller/AI 自主决定，不需要人类事前批准；高影响动作仍需独立 AI 复核、员工申诉和审计。
- 解雇、移除模型订阅和释放编制必须由人类 Boss 最终批准。
- 人类只参与解雇和事后审查，可以调取证据、推翻结论和要求纠正，不管理其他日常绩效动作。
- KPI 不达标只是证据信号，不直接触发解雇；主控不能在无继任者时被解雇。

### 3.8 内部项目管理与协作

- 具备 `project.create`、`requirement.create` 能力的管理角色可以创建项目、需求和里程碑，角色名称不固定。
- 需求必须通过就绪审查并包含验收标准，随后拆分为可独立执行的任务。
- LLM 生成拆分提案，控制面校验验收覆盖、依赖、能力、权重、风险和独立性。
- 单个任务初始估算 0.5～1 人日，超过 2 人日继续拆分；单需求默认 3～12 个任务。
- 子任务总权重不得超过原需求，自动拆分不等于自动派工。
- 高风险拆分沿管理链逐级审批，提交人不能自审。
- 员工 WIP 容量按任务权重设为 3、5 或 8，完成前不释放占用。
- 认领评分加入负载、稀缺能力、公平性和连续高负载惩罚；强能力员工优先但不垄断。
- 改派由直接 Leader 审批，按配对、拆分、改派、升级顺序处理。
- 系统按能力、WIP、成本和依赖推荐负责人；开发认领任务，不能直接跳过需求拆分。
- 测试提交缺陷，开发修复，测试复测关闭；缺陷始终关联需求和任务。
- 每个项目、需求、任务和缺陷都支持线程讨论、证据引用、待办和结论。
- 高风险方案可发起对抗评审或红队审查；评审者不得为作者本人。
- 高权重或核心架构需 2 名独立评审且至少 1 名专家；安全、数据迁移和发布需专业评审与管理审批。
- 评审必须给出证据化 findings；所有必需评审通过且无阻断项才能 Approved。
- 争议必须有时限，超时由具备决策能力的角色裁决；被否决意见保留在审计和决策记录中。
- 技术评审判断质量，管理裁决沿直接 Leader 至 Boss 逐级处理，红线和租户隔离不可推翻。
- 项目状态、认领、依赖和关闭条件由控制面确定性管理，LLM 只负责分析、建议、拆分和讨论。
- 开发、测试、评审、对抗、裁决、验收、发布、招聘和知识沉淀等都使用统一 Task Type。
- TaskTypeDefinition 决定所需能力、Tool Profile、权重规则、Done 模板、证据和 KPI。
- ReviewTask、DebateTask、AdjudicationTask 是可认领、可加权、可验收的正式任务，不是普通聊天。
- EmployeeWorkLedger 按任务类型、权重、质量、能力匹配、成本和证据记录员工实际贡献。
- 同一成果只能有一个主任务权重，父子和协作任务不得重复计分。

### 3.9 通信标签与双图路由

- 管理链由组织树生成，负责汇报、资源、绩效和审批。
- 专业链由岗位标签和能力生成，负责技术、产品、质量等问题的专业升级。
- 专业路由可以沿组织树向上查找并跳过没有目标标签的管理岗位，直接联系最近匹配的祖先岗位。
- 技术标签不需要贯穿每一层；例如开发可以穿过项目经理直接向架构师咨询。
- 通信路由只决定“可以问谁”，不扩大 Tool、预算、组织或审批权限。
- 项目成员关系可以临时覆盖默认路由，但不能跨租户或跨未授权项目。
- 标签和路由由控制面版本化管理；组织变化后自动重算并保留审计。

### 3.10 Agent 上下文与缓存

- 上下文由系统与岗位规则、TaskCheckpoint、当前工作上下文和长期记忆检索组成。
- 输入预算达到 70% 时准备压缩；目标、约束、决策、失败、反证、证据和下一步不得丢失。
- 超长工具结果进入 RustFS，模型只接收摘要、关键片段和引用。
- 上下文按稳定前缀到动态后缀组装，优先复用系统规则、岗位章程和 Tool Schema 缓存。
- 对话采用追加方式；Charter、岗位、权限或安全策略变化时主动失效。
- OpenAI 与 Anthropic 各自按原生缓存语义计量，不做协议转换。
- ContextPacket 记录版本、引用、排除项、token、压缩和缓存信息。

### 3.11 提示词、技能与入职配置

- SystemPromptTemplate、PositionCharterVersion 和 SkillPackageVersion 都是不可变版本资产。
- TaskRun 固定 PromptBundle，不中途切换系统提示、岗位 Charter 或技能版本。
- 招聘使用中立白板评测，不安装生产岗位 Charter 和高级技能。
- 聘用后自动安装平台基线、岗位 Charter 和 Starter Skill Pack。
- 主控或岗位负责人按能力和任务渐进分配进阶技能。
- 员工可进化个人技能，但必须通过评测、审查和试点才能成为组织公共资产。
- 安装技能不自动授予权限；跨租户公共资产后置并需匿名化与平台审核。
- 版本变化触发相关稳定前缀缓存失效，所有发布和回滚均可审计。

### 3.12 Agent 工具循环与成本评审

- 单次执行片段有轮次、调用、失败和无进展限制；到软限制后保存检查点并立即续跑。
- 重复调用、循环模式和部分成功由确定性程序检测与恢复。
- 去掉任务级成本硬上限；50% 预警、80% 通知直接 Leader、100% 暂停评审。
- 模型和推理强度绑定员工，任务中不可临时更换。
- 模型失败只允许同模型、同版本、同推理强度和同协议恢复，禁止自动跨模型降级。
- 算法连续 2 次失败或 5 分钟持续不可用后生成 ModelUnavailableEvent，上报直接 Leader。
- 员工运行状态由算法维护，界面可拟人显示“生病、疲惫、忙碌、休息”，底层记录真实原因。
- 可用率、疲惫率、故障率、恢复时间和反复异常进入 KPI，但必须区分员工、平台/模型和管理原因。
- 模型目录每日从 models.dev 同步并版本化，BYOK 自动预填已有价格。
- models.dev 缺失的价格由用户补充；之后 models.dev 提供同字段时自动覆盖。
- 每日消耗按请求发生时有效的价格快照计算，历史账目不追溯改写。
- cheap/mid/premium 档位由 models.dev 数据自动计算，不手工维护。
- 成本预警沿管理链逐级上报，合理则放行，不匹配则调岗，内部无法解决才到 Boss。
- 公司 Charter 全局硬预算、安全红线和租户隔离仍保留。

### 3.13 Agent 聊天与协作

- 支持私人会话、项目群、岗位群、主题群和线程回复。
- `@` 是定向通知和路由信号，不自动派工，也不绕过通信权限。
- 消息类型包括任务、委派、求助、交接、评审、决策、打断、状态和普通聊天。
- 委派和交接使用显式状态机；接收者可以带理由拒绝。
- P0/P1 消息可唤醒员工，普通消息进入摘要或队列。
- 聊天可作为弱证据加权召回，并采用“通知 → 摘要 → 相关消息 → 完整线程”的渐进披露。
- 聊天不直接修改任务状态；重要内容可提升为 Task、Requirement、Defect 或 Decision。
- 私人会话默认仅参与者可见，群聊按项目和岗位范围隔离。

### 3.14 模型评测与回归

- 评测结果按模型版本、推理强度、PromptBundle、Tool Profile、Runtime、数据集、评分策略和 seed 建立复用键。
- 同一公司内只复用完全匹配的结果；跨租户默认不共享。
- BenchmarkSuite、DatasetVersion、BenchmarkCase 和评分规则版本化，保存来源、hash、许可证和脱敏状态。
- 密封集不向员工、模型和普通管理界面开放；评测用例不进入生产记忆、Skill 或 Prompt。
- 新模型运行完整核心集，每日 canary、每周核心回归、每月全量，Prompt/Skill/Tool 变化运行受影响集合。
- 安全和租户隔离案例 100% 通过，P0/P1 为 0，核心案例 100%，整体 ≥80%，单维度 ≥70%。
- 确定性测试优先，LLM Judge 和人工抽检补充；Judge 独立且版本固定。
- 评测通过不自动绑定员工，失败不自动触发处罚。
- 数据集分为 development、calibration、holdout；holdout 仅评测服务可读，canary 检测泄漏，每 6 个月至少轮换 20%。
- 污染检测使用精确 hash、规范化近似重复 0.92、已知污染记录和交叉泄漏检查；受影响结果 Quarantined。
- Judge 是具备 evaluation.judge 能力的正式员工和独立运行时，优先不同模型；仅一个模型时允许同模型不同运行时，禁止自评和上下文共享。
- Judge 每版本首次使用前由两名独立人工盲评至少 100 条或 20% 案例，一致率 ≥85%、加权 κ ≥0.70，每月抽检。
- 最小样本为核心 100、安全 50、单维度 30、每日 canary 20；每案例固定 seed 运行 3 次，核心和安全 3/3，其他至少 2/3。
- 整体通过率 ≥80% 且 Wilson 95% 下界 ≥75%，单维度 ≥70% 且下界 ≥65%；基线比较使用 McNemar 精确检验。
- 结果分为 Approved、Rejected、Quarantined、Inconclusive；安全失败立即隔离，失败不自动换模型或处罚员工。

### 3.15 数据 Schema 与存储边界

- 生产关系数据统一 Postgres，SQLite 仅用于单租户开发和测试。
- 二进制快照、成果、报告和数据集统一 RustFS，直接使用 S3 SDK，不保留 ArtifactStore 多实现抽象。
- 活动 Git 工作区使用 Runner 本地目录或容器隔离目录，属于临时计算空间。
- 租户业务表采用共享表 + tenant_id + 强制 RLS，应用角色不得绕过。
- 单库短事务维护即时不变量，跨模块使用 Outbox、Inbox 和 Saga。
- 状态在数据库中存稳定 snake_case 字符串，在代码中使用密封引用类型包装。
- MVP 不预先分区，高增长表按实际规模启用分区。

### 3.16 部署、升级与迁移

- MVP 和自托管采用单机 Docker Compose + systemd 监管。
- 四个服务、两个前端、Postgres 和 RustFS 按同一 ReleaseManifest 版本集发布。
- 基础镜像尽量按 digest 固定，本地构建记录镜像 ID；升级期间只允许 N/N-1 混跑。
- 升级顺序为 Drain → Backup → Expand → Deploy → Smoke → Resume → Contract；备份默认关闭，跳过时记录风险接受。
- 生产禁止启动时自动迁移，迁移使用独立角色、advisory lock 和可恢复回填。
- 应用只能在 Expand 且数据兼容时回滚；Contract 后必须前滚或恢复备份。
- API、事件、Runner 和配置必须显式声明兼容版本。

### 3.17 可观测性与测试基线

- 四个服务和两个前端统一使用 OpenTelemetry SDK。
- 后端支持 `off`、`local`、`otlp`、`elastic` 四种 Profile，自托管默认 `local`。
- `local` 使用 stdout/journald 或轮转日志；`otlp` 接入用户已有后端；`elastic` 才启用 Elasticsearch、Kibana 和 APM Server。
- Elastic 组件放入可选 Compose Profile，默认不启动；指标、日志和追踪可独立开关。
- 遥测健康不进入核心 Ready 检查，后端故障不阻塞业务。
- 不记录密钥、完整 Prompt、源码、敏感工具参数和密封评测集。
- Elastic Profile 下 SLO 和错误预算驱动 L0～L3 告警；off/local 不要求 Kibana、APM 和运行时错误预算。
- xUnit、真实 Postgres/RustFS 集成、Provider 契约、E2E、Playwright、安全、混沌和升级测试始终进入发布门禁。
- 整体覆盖率 ≥80%，关键模块 ≥90%；MVP 容量基线为 20 员工、40 并行任务。

### 3.18 提示词与工具输出注入防御

- 外部网页、Issue、代码、文档、消息、Tool/MCP 输出和记忆片段均作为不可信数据处理。
- 内容保存来源、hash、taint 和风险信息；摘要、压缩和记忆提升不得洗白 taint。
- 任务通过 TaskGrant 预授权工作区、Tool、网络、预算和动作范围，Grant 内不逐步审批。
- 确定性检测优先，模型检测只作辅助；默认标记、清理并继续安全分析，不因误报中断低风险工作。
- 每次 Tool Call 由执行层独立校验权限，内容不能激活 Tool、扩大 Capability 或伪造审批。
- 只有突破 Grant、权限、预算或红线时才暂停并沿管理链升级。
- 权限提升、跨租户和未审批高风险动作零容忍；注入误报导致的任务中断目标为 0。

### 3.19 记忆投毒与纠错

- 记忆拆分为 MemoryClaim，每个 claim 独立保存来源、证据、置信度、验证、taint、冲突和引用。
- 检测来源可信度、证据缺失、同源重复、冲突、异常灌入和摘要置信度异常。
- 高风险 claim 立即停止召回，低风险降权复核；只隔离受影响内容。
- CorrectionTask 是可认领、加权、验收的正式任务，复核者与作者和来源提交者分离。
- 纠错生成新版本并引用旧 claim，不静默修改原文，支持反证申诉。
- MemoryImpactRecord 追踪员工、任务、摘要、决策和外部动作引用。
- 在途任务重新检索，已完成任务按状态创建缺陷、复审或回归，不自动回滚。
- 纠正通过 Outbox 传播到向量、全文、图、缓存、派生摘要和通知。

### 3.20 工具与插件供应链

- Tool、MCP、Skill、依赖、容器镜像和安装包统一登记为 SupplyChainArtifact。
- 制品按版本和 digest 固定，保存签名、来源、许可证、SBOM、扫描和审批。
- 准入必须经过签名、漏洞、许可、权限、网络和隔离试运行审核。
- TaskRun 固定制品版本，不中途升级；已批准制品免逐次审批。
- 安装、升级、扩权或突破沙箱才需要新审核。
- 撤销按 digest 查询影响、停止新加载并轮换可能暴露的凭据。
- 不删除历史证据，不处罚使用已批准制品的员工。

### 3.21 PII 与秘密脱敏

- 数据分为 Public、Internal、Confidential、Restricted，秘密和敏感 PII 默认 Restricted。
- 在 API、聊天、Tool、模型出站、记忆、Artifact、日志、Trace、导出和通知边界执行 DLP。
- 秘密只存在于密钥系统，业务系统只保存 `secret_ref`；高置信秘密立即阻止并评估轮换。
- PII 默认遮蔽、令牌化、假名化或匿名化，模型上下文只发送必要字段。
- 审计只保存规则、字段类型、对象、动作和哈希，不保存秘密或完整 PII。
- 删除通过影响图传播到数据库、对象、索引、缓存、遥测副本和令牌映射，并输出删除证明。
- 误报不得阻断安全任务；例外必须绑定范围、原因、负责人和到期时间。

### 3.22 审计完整性

- 审计支持 `standard`、`worm`、`anchored` 三种 Profile，默认 standard。
- 业务状态与审计事件同事务提交，审计角色只允许 INSERT/SELECT。
- 每个租户和审计流维护连续 seq 和 event_hash 哈希链。
- 定期生成签名 Merkle 检查点并写入版本化 RustFS。
- worm Profile 使用 Object Lock 或法定保留；anchored Profile 增加外部独立 root 锚定。
- 验证器重算链、Merkle、签名和保留状态，失败进入安全事件。
- 审计不保存秘密和完整 PII，外部锚定只发布 root 和范围元数据。

### 3.23 离职、调岗与再入职

- 每个员工拥有全局唯一、不可变、永不复用的 `employee_no`。
- 调岗保留工号和运行时；再入职复用工号但创建新任职周期、会话和凭据。
- 统一评级持续很低时进入 `PendingRemovalQueue`，不直接解雇。
- 主控只能决定不录用候选人；录用、再入职和移除订阅必须由 Boss 最终批准。
- 公司成果和组织资产保留，项目内容交接；个人记忆、私人聊天和私有草稿默认隔离。
- 秘密吊销或轮换，不转移、不继承。
- 离职移除运行/模型订阅、释放编制并输出交接与删除证明；主控无继任者时不能移除。

### 3.24 内容安全

- 检测覆盖用户输入、员工输出、聊天、Tool、代码、文档、多媒体、记忆和对外发布。
- 内容分为 Allowed、AllowedWithLabel、Restricted、RequiresReview、Prohibited。
- 检测管线和 moderation 后端可插拔，分类器不作为唯一法律判断。
- 正常内容自动放行，模糊场景复核，红线内容阻止并升级。
- 默认只限制违规内容或动作，不冻结员工全部工作，不因误报处罚员工。
- 对外发布必须通过内容安全门禁，且不替代发布审批。
- 审计只保存脱敏元数据，法律取证单独加密并限权。

### 3.25 安全事件响应

- 安全事件分为 SEV1～SEV4，由 Incident Commander 按能力任命。
- 允许预授权自动撤销凭据、冻结 Runner/Tool/制品、隔离容器和暂停任务。
- 删除数据、关闭租户、对外声明和联系监管等动作仍需审批。
- 证据加密、哈希、WORM 并全程审计，普通聊天不保存秘密和完整 PII。
- SEV1 立即通知 Boss、IC 和受影响租户，状态页只发布脱敏影响。
- 恢复需根因控制、凭据轮换、干净版本、对账、监控和 IC 批准。
- 复盘默认无责归因员工个人，改进任务进入项目闭环。

### 3.26 账户身份与无邮件找回

- 本期优先支持账号密码注册登录、GitHub OAuth 登录和一次性恢复码自助找回。
- 密码使用 Argon2id 哈希，登录和注册限流且不泄露账户是否存在。
- OAuth 使用 Authorization Code + PKCE、state 和精确 redirect URI。
- 外部身份以不可变 GitHub user id 绑定，不使用 login 作为主键。
- GitHub 已验证邮箱可自动合并到唯一匹配的已有账户。
- 本地未验证邮箱不得自动合并，也不能仅凭相同邮箱接管账户。
- 恢复码只显示一次，服务端只存不可逆哈希，单次使用。
- 找回成功后用户设置新密码，并撤销旧会话和 Refresh Token。
- 备用邮箱、短信、安全问题、其他社交登录和完整人工找回暂缓。

### 3.27 企业 OIDC 与会话

- 租户 OIDC 企业登录提前到第一梯队，SAML 暂缓。
- 使用 Authorization Code + PKCE、state、nonce，并严格校验 ID Token。
- 账户身份使用 `issuer + sub`，新用户必须先邀请或预置。
- 组到能力映射显式配置，不自动授予 Owner。
- SSO 用户优先委托 IdP MFA，运营 MFA 保持强制。
- BFF、设备管理、会话家族轮换和本地 WebAuthn/TOTP 后置。
- 保留现有 Cookie/Token、CSRF、基础退出撤销和密码找回撤销。

### 3.28 多股东与多公司

- 账户与租户解耦，一个账户可以加入或拥有多个租户。
- 第一梯队保持一租户一公司，多家公司通过多个租户实现。
- 每个租户恰好一个 Primary Owner，可有多名 Co-Owner。
- Primary Owner 管理订阅、主所有权转让和租户删除。
- OwnerDelegation 限时、限范围，默认最长 30 天且不能转授权。
- 不能移除最后一个所有者，主所有权转让需要目标明确接受。
- 切换租户时服务端校验成员关系并重新签发租户作用域会话。
- 跨租户不共享密钥、预算、员工、记忆、聊天、成果和审计。

### 3.29 账户与租户软删除

- 停用、账户注销和租户删除分离。
- 删除请求立即逻辑删除并停止登录、任务、召回、搜索和普通访问。
- 账户恢复窗口 30 天，租户 7 天；宽限期可重新认证恢复。
- 账户注销前必须处理唯一 Primary 所有权，Co-Owner 注销不删除公司。
- 软删除数据加密隔离，密钥和 Token 立即撤销。
- 恢复窗口结束后物理清除并生成 DeletionProof。
- 备份启用后最长保留 35 天，tombstone 默认 1 年，恢复备份必须重放删除状态。
- 法律保留只阻止物理清除，不恢复用户访问。

### 3.30 在线保留与归档

- 数据按统一保留类进入 Hot、Archive、Cold 三层。
- 消息在线 90 天加归档 1 年；任务在线 180 天加归档 3 年。
- 账本和审计在租户终止后保留 7 年。
- 日志 14 天、指标 30 天、Trace 7 天，原始模型缓存最多 30 天且默认不归档。
- 结构化归档使用 JSONL + Zstandard，按月执行并校验数量、哈希和 manifest。
- 普通 Agent 只查 Hot；归档恢复需授权、隔离和审计，临时副本默认保留 7 天。
- 软删除和 tombstone 优先于归档，法律保留不恢复用户访问。

### 3.31 可选备份与恢复

- 备份能力开关化，默认关闭且实施后置，不作为 MVP 优先项。
- Postgres 全量、WAL/PITR、RustFS、密钥库、异地副本和恢复演练分别控制。
- 未启用组件不承诺 RPO/RTO，启用后按实际覆盖计算有效目标。
- 全量目标为 RPO 24 小时/RTO 8 小时，账本审计为 15 分钟/4 小时，密钥库为 15 分钟/2 小时。
- 滚动备份最长 35 天，长期保留由 Q-031 归档承担。
- 升级可记录风险接受后跳过备份，但不得伪造备份成功状态。
- 归档、审计、RustFS 持久化和软删除不受备份开关影响。

### 3.32 AI 产出归属

- 租户员工在任务范围内生成的代码、文档、设计、数据整理结果和公司志归租户所有。
- Regent 不主张业务产出所有权，只保留运行、托管、备份、支持和审计所需有限许可。
- 用户输入和预先存在的知识产权仍归原权利人。
- 第三方材料、开源依赖、Tool 返回数据和数据集仍受原许可证约束。
- 提供商条款只转让其拥有的输出权利，不覆盖第三方权利，也不保证版权可保护性。
- 租户内容默认不用于平台训练、公共基准或跨租户资产。
- UnknownRights 默认不得对外发布，重要 Artifact 必须保留来源和人类贡献记录。

### 3.33 公平招聘

- 招聘只按岗位相关能力评分，面试前固定能力矩阵、题目、权重和门槛。
- 隐去身份和模型品牌，使用等价题目、时间、工具和预算，至少两名独立评分者。
- 禁止使用性别、年龄、种族、国籍、残疾、姓名、照片、口音等受保护特征。
- 多语言评估必须检查语义等价，不因非母语表达扣分，除非相关能力是岗位要求。
- 每个招聘周期执行模型、版本、语言和自愿分群的偏差审计。
- 群体选择率比值低于 0.8 时触发调查，但不自动认定歧视或改变个人结果。
- 候选人可申诉、提交反证、申请合理便利或复测；申诉期间暂停最终淘汰。
- 公平修正不得降低安全、质量和核心能力门槛，Boss 保留最终录用权。
- 候选人资料决策后默认 180 天清除。

### 3.34 开源许可与商业边界

- 第一方源码、测试、构建、部署、Schema、API 契约、文档和官方示例统一采用 Apache-2.0。
- 公开发布必须包含 LICENSE、NOTICE、SBOM、依赖许可证清单和第三方通知。
- 第三方依赖、模型、数据集和素材保留各自许可证。
- 不设闭源商业版，不锁定核心或默认企业功能；托管、支持、SLA 和运维服务可以收费。
- 贡献按 Apache-2.0 第 5 条提交，使用 DCO Signed-off-by，不强制转让版权。
- Regent 名称、Logo 和商标不随代码许可证授予。
- 租户产出不自动适用 Apache-2.0。

### 3.35 仪表盘信息架构

- Boss 首屏依次展示公司状态、待我处理、项目健康、预算成本、组织产能、风险审计和最近决策。
- 首屏回答健康、风险、钱、组织和待决策五个问题，不展示日常任务、全部消息和原始日志。
- 项目工作流阶段与健康状态分开；健康状态由确定性规则计算。
- 导航最多两级：总览、项目与交付、组织与员工、消息与协作、模型与预算、知识与公司志、治理与升级、设置。
- 行动中心统一聚合升级、告警、安全、预算、发布、模型、删除、审计和许可证异常。
- 卡片必须可下钻、显示负责人、等待时间、下一步、数据时间和新鲜度。
- Butler 摘要不能覆盖确定性状态，菜单隐藏不替代 API 鉴权。
- 运营平台页面不进入租户导航。

### 3.36 审批委托与缺席

- 动作分为 T0 自动、T1 运营、T2 治理、T3 所有者和禁止五类。
- 人类缺席时，Controller 与直接下一层先在现有授权内协商。
- 只有双方明确同意、权限和预算充足且不触红线时才自主执行；否则进入委托或备用审批人流程。
- ApprovalDelegation 只委托给 Active 人类成员，需双方确认、限时、限范围、可撤销且不可转授权。
- 被委托人不能自我批准或批准利益冲突事项；解雇只能委托给人类 Boss/Co-Owner。
- 主所有权转让、租户删除、订阅变更、所有者管理、法律声明和不可逆大规模清除不可普通委托。
- 默认 SLA 为 Critical 30 分钟、High 4 小时、Normal 24 小时、Low 72 小时；超时默认拒绝。
- 紧急安全遏制仍按预授权执行，不等待审批。

### 3.37 国际化与本地化

- 产品界面第一梯队支持 zh-CN 和 en-US，租户可设默认语言，用户可覆盖。
- 缺失翻译回退源语言并记录，不显示资源 key。
- 数据库和 API 时间统一 UTC/RFC 3339，显示使用 IANA 时区和 locale。
- 日期、数字、百分比和排序按 locale 格式化，币种显式使用 ISO 4217。
- Agent 输出默认跟随租户语言，任务可覆盖；代码标识、API 字段、审计 payload 和法律原文不自动翻译。
- 翻译保留来源、版本和标识，安全、法务和审批文案必须人工复核。
- 中文技术文档保持权威，英文公开 README、安装和 API 文档同步发布。
- 完整无障碍支持后置，不进入 MVP 发布门禁；后续以 WCAG 2.2 AA 为目标。

### 3.38 公司作息与调度

- 公司默认全天 24 小时可运行，使用 IANA 时区，用户可设置任意工作、静默或禁用窗口。
- 支持跨午夜窗口、多窗口、岗位覆盖和节假日；不默认禁止夜间。
- 用户禁用窗口内的普通任务排队，Controller 和 Butler 跟随策略但避免无意义频繁唤醒。
- 用户可配置低价窗口、适用 Provider/模型、折扣来源和有效期。
- 可延期 P2/P3 任务在截止时间允许时优先安排到低价窗口；折扣未知时按有效价格快照记账。
- P0/P1 和紧急任务不等待低价窗口。
- 到达禁用窗口或排班结束时，普通任务保存 TaskCheckpoint、释放租约并标记 DeferredUntil。
- P0 安全、生产事故、红线、L2/L3、硬预算和密钥风险可立即唤醒。
- 临时加班必须限时、限范围并在预算内，超预算仍走审批。
- 用户禁用窗口、休息和假期不计入员工可用率分母，不因按设置休眠扣绩效。

### 3.39 CI/CD 与本地部署

- 源码、Issue、PR 和版本只使用 GitHub。
- GitHub 只打 `v*` 版本 Tag，不发布镜像或二进制制品。
- GitHub Actions 只负责编译、测试、扫描和迁移检查。
- 自托管部署使用本地 Docker Compose + systemd，从对应 Tag 检出源码并构建。
- PR 必须通过编译、测试、安全、许可证和迁移检查后才能合并。
- 本地构建记录 Tag、commit、基础镜像和生成镜像 ID，依赖使用 lock file。
- 本地保存当前和上一版本镜像 ID，回滚优先复用旧镜像，缺失时从旧 Tag 重建。
- CI 不持有生产模型密钥，外部 PR 不获得秘密。
- 不使用 GHCR，不引入多 Git 平台适配、多环境晋升、Kubernetes 或独立制品管理平台。

### 3.40 成本归属、分摊与异常

- 钱账是唯一成本事实，员工、岗位、项目和公共成本是视图，不重复计费。
- 优先按任务所属项目归属，其次按显式项目或成本中心归属；无法归属进入 `Unallocated` 队列。
- Butler、公共评测和基础设施无项目成本默认进入公司公共成本。
- 公共成本不自动平均分摊；显式规则必须版本化、权重合计 100% 并审批，分摊不新增费用。
- 项目预算属于租户预算，默认软限制；租户月度预算仍是硬限制。
- 预算不自动结转，只有所有者可显式批准未使用项目预算结转。
- 第一梯队只做确定性异常检测，不自动改预算、换模型或惩罚员工。
- 任务预算 100% 暂停评审；项目预测超预算 120% 为 L2；租户预测超硬预算为 L2、超 110% 为 L3。
- 模型价格短时间变化超过 20% 停止自动路由；账单差异超过 1% 或配置阈值时对账。
- 金额使用最小货币单位整数，只保存原币金额和币种，不同币种分别统计、不直接相加；迟到费用按发生周期归属，关闭周期通过更正条目处理。
- 历史成本保留发生时员工、岗位和项目快照。

### 3.41 模型运行边界

- 当前不需要本地 GPU，不实现 Ollama、本地模型档或 GPU 调度。
- 模型运行只支持 OpenAI 和 Anthropic 云端原生端点。
- 不保留 `ollama_openai` 协议、Ollama Provider 插件或本地 GPU 兼容层。
- 员工容器不挂载 GPU，Runner 不上报本地推理资源。
- 本地推理如将来重新引入，必须作为新需求评审。

### 3.42 内部通知中心

- 第一梯队只实现仪表盘内部通知中心。
- 不实现 Telegram、邮件、短信、Slack、飞书、企业微信、Teams 或通用 Webhook。
- 通知先持久化，再通过 SignalR 实时推送；推送失败可重新拉取。
- L0/L1 记录或摘要，L2 站内提示，L3/SEV1/SEV2 立即站内通知。
- L3/SEV1 不受普通静默时段限制，其他通知遵守 Q-041 工作窗口。
- 通知只提供摘要和授权链接，不包含秘密，也不能替代正式审批。
- 外部渠道全部后置，当前不保留通知 Provider 接口。

### 3.43 公共 API 与生态边界

- 当前只保留内部 `/v1` API、`ToolManifest + AIFunction` 和内部 MCP 工具面。
- MCP 仅用于 Butler 只读工具和模型评测。
- 租户内部 Tool、Skill 和依赖继续按 Q-021 审核、签名和撤销。
- 不提供公共 REST API、对外 API Token、OAuth Client、公共 SDK 或出站 Webhook。
- 不建设 MCP 市场、插件市场、发布者后台、跨租户 Skill 分享或第三方自动安装更新。
- 内部 `/v1` 不构成公共兼容性承诺。

### 3.44 自托管安装与离线升级

- 自托管只使用 GitHub 版本 Tag 源码、Docker Compose、systemd 和仓库内简单脚本。
- 不提供二进制安装器、GUI 安装器或一键安装包。
- 直接使用 Apache-2.0，不提供 License Key、激活服务器或电话回拨。
- 不自动检查、下载或安装更新；用户必须显式指定版本 Tag。
- 离线仅支持用户自备源码、基础镜像和依赖缓存，禁止联网回退，缺失依赖必须快速失败。
- 云端模型导致完全断网时无法推理，不承诺完整离线运行。
- 升级失败保留旧 Tag 和旧镜像，按 Expand/Contract 边界回滚或前滚。

### 3.45 容量与性能基线

- 当前只承诺单租户、单机部署的聚合容量。
- 基线为 20 员工、40 并行 TaskRun、100 任务/小时、1000 消息/小时、100 模型请求/分钟、2 倍 15 分钟突发和 24 小时 soak。
- 多租户大规模容量后置，公平性测试最多使用 5 个模拟租户。
- 普通读 API P95 ≤300ms，普通写 API P95 ≤500ms。
- Pending Task、员工待处理项、消息积压、Outbox 和模型在途请求必须有默认上限和背压。
- 共享 Runner 按租户加权轮询，单租户连续占用共享槽位最多 3 次后让出。
- 单租户压测不得使其他租户普通 API P95 劣化超过 20%，合格任务等待不得超过 30 秒。
- Provider 可用性单独统计，容量测试摘要进入发布门禁。

### 3.46 企业合规与支持边界

- 当前支持用户在自己的服务器、内网或 VPC 中按 Tag 源码私有部署，不提供托管式 BYOC 或企业部署团队。
- 数据驻留由部署位置和模型 Provider/区域选择决定，不提供跨区域编排。
- 租户通过 `ComplianceProfile` 配置地区、行业要求、允许的 Provider/模型/区域、数据分级、保留、审计 Profile、备份要求和外部共享范围。
- 提供 baseline、strict 和自定义预设；必需控制项不满足时 fail closed。
- 保留审计、删除证明、DLP、SupportGrant、SBOM 和安全事件证据，但不宣称 SOC 2、ISO 27001 或等保认证。
- 不提供自动客户合规审计包、法律意见、商业 SLA、24×7 值班、专属支持或迁移协助。
- 当前仅提供公开 GitHub Issue 和文档支持。

## 4. 产品目标与成功指标

### 4.1 产品目标

- **G1 自主启动**：租户完成章程和模型配置后，公司可以自动启动并形成组织。
- **G2 自主发现**：公司能够产出带来源、经过交叉验证的产品机会与简报。
- **G3 自主交付**：公司能够开发、测试、修复并形成可体验的产品版本。
- **G4 独立验收**：产品能够由与实现者独立的验收职能按真实用户目标验证，而不是开发组自评。
- **G5 可控治理**：人类可以随时了解状态，并对外部动作、超预算和红线事项做最终决策。
- **G6 商业可用**：平台能够支撑多租户 BYOK、本地订阅/配额账本、自助数据导出与自托管；真实支付、跨环境导入和托管退出仍后置。
- **G7 组织进化**：员工能够把有效做法沉淀为可复用工作流，Leader 能够审查、采纳并持续改进。
- **G8 知识积累**：个人经验可以安全沉淀为组织记忆和知识库，并支持准确召回、持续验证和遗忘。
- **G9 持续改进**：每名员工都能自驱动优化，公司通过 KPI 和证据持续调整员工、岗位与流程。

### 4.3 阶段指标口径

- 员工遇到问题先自行解决，再沿组织树逐级向上：直接上级 → 更高层 Leader → Controller → Boss。
- 内部升级属于正常自治机制，不计为人工介入，但必须记录次数、耗时和结果。
- 只有内部链路确实无法解决的问题才提交 Boss；必要审批单独统计，不算失误。
- 所有失误、错误重试、错误交接、质量缺陷和无效尝试都必须记录，即使后续修复也不能抹除。
- 一次尝试从阶段入口到退出门禁；系统自动重试仍算同一次。
- 成功率以“一次自主通过率”为主，“最终自主完成率”为辅；耗时同时记录中位数和 P90。

| 阶段 | 一次自主通过率 | 最终自主完成率 | Boss 升级率上限 | 目标耗时 |
|---|---:|---:|---:|---:|
| R1 自主启动 | ≥90% | ≥95% | ≤10% | ≤15 分钟 |
| R2 自主调研 | ≥60% | ≥80% | ≤20% | ≤4 小时 |
| R3 自主交付 | ≥30% | ≥70% | ≤30% | ≤72 小时 |
| R4 治理与运营 | ≥95% | ≥98% | ≤5% | 按动作时限 |
| R5 SaaS 启动 | ≥95% | ≥98% | ≤5% | ≤15 分钟 |
| R6 开源自托管 | ≥99% | ≥99% | ≤10% | ≤30 分钟 |

以上为 dogfooding 初始值，至少积累 10 次尝试或 2 周数据后校准；R3 耗时需结合 MVP 范围和统一完成标准重算。详见 [Q-001 决策记录](./Regent-Agent-待确认项.md)。

## 5. 产品范围

### 5.1 首个自主闭环

- 租户创建公司与章程。
- 配置可用模型池。
- 启动主控，由主控为自己创建岗位并规划初始组织。
- 自主完成市场调研、候选机会筛选和产品简报。
- 调研结论必须包含来源，关键数据需要交叉验证。
- 产品简报必须包含 MVP 范围和成功指标。

### 5.2 完整产品闭环

在首个自主闭环之上，增加：

- 自主招聘、面试、组织扩张与考核。
- 产品开发、自动化测试、缺陷修复与版本管理。
- 独立体验官验收、优先级调整和复测。
- 产品发布、运行时观察、迭代与项目终止复盘。
- 公司记忆、审计、周报、预算报告和可选备份恢复。

### 5.3 SaaS 与开源商业化

- 注册、登录与租户创建；当前版本不依赖邮件验证。
- BYOK 模型配置向导。
- 套餐、配额、订阅计费与租户管理。
- 托管服务与全套自托管两种部署路径。
- 自托管使用版本 Tag 源码和 Compose 脚本；租户自助导出与校验迁移包已实现，跨环境导入、密钥迁移与托管退出仍后置。

### 5.4 MVP 边界

MVP 是单租户、自托管可运行的完整自主交付闭环，从 Charter 到独立验收通过的发布候选。里程碑 A“公司成立”只要求主控自主建岗、规划组织并产出产品简报。

MVP 必须包含租户与章程、控制面、网关、Runner、Tool 体系、动态组织、项目管理、沙箱与存储、通信路由、交付质量、发布回滚、治理审计、最小仪表盘、基础记忆和 KPI 复核。

MVP 不含在线支付、完整运营平台、多租户商业化、一键安装包、高级图谱、自动招聘评分平台、自动绩效处罚、公共 API、公共 SDK、出站 Webhook、MCP/插件市场、跨租户 Skill 分享、企业认证声明、商业 SLA、专属支持、SAML 和完整 Butler 报告；OIDC 企业登录按 Q-028 提前，合规策略可按 Q-050 配置。

MVP 退出条件：

1. 空白环境启动到 Active 组织 ≤15 分钟，产品简报 ≤4 小时。
2. 至少 3 次端到端尝试，其中 2 次形成独立验收通过的发布候选。
3. 关键场景 100% 通过，P0/P1 清零。
4. 发布失败可回滚，Runner 崩溃不丢任务、成果和账本。
5. 模型调用有预算预留和计量，硬预算、租户隔离和密钥边界测试通过。
6. 备份可实际恢复，关键决策、成本和组织变更可审计。
7. Boss 只处理升级事项，失败项目能复盘并沉淀经验。

### 5.5 非目标

- 不预设公司的第一个产品方向。
- 不承诺完全消除人类决策；高风险事项必须保留人工审批。
- 不涉足硬件、重资产或需要特殊资质的行业。
- 不提供灰产、侵权、冒充人类或违法内容相关能力。
- 不在跨运营方边界提供“控制面托管、用户自带 Runner”的半信任模式。
- 不为了尚未出现的规模过早引入重型分布式中间件。
- 当前版本不接入邮件服务商；本地邮件验证与邮件找回不在本期范围，第一梯队支持账号密码、GitHub 登录和恢复码自助流程。

## 6. 核心用户旅程

### 6.1 新租户启动

1. 股东通过账号密码或 GitHub OAuth 注册并登录，并保存一次性恢复码；本地邮箱未验证时不可触发自动合并。
2. 配置模型池与密钥。
3. 使用模板或自定义内容编写公司章程。
4. 设置预算、站内通知偏好和审批偏好。
5. 启动公司，系统创建主控；主控为自己建岗并规划初始组织。
6. 股东进入仪表盘观察启动过程；后续可创建新租户或在已授权租户间切换。

验收：新用户能够在没有人工部署编排的情况下启动自己的公司，并看到可解释的启动状态。

### 6.2 自主发现产品机会

1. 主控根据章程和目标分派调研与产品定义能力。
2. 具备调研能力的岗位从多个来源调研并记录证据。
3. 具备产品定义能力的岗位按可构建性、周期、成本和资质约束筛选机会。
4. 产品定义岗位输出带成功指标的产品简报。
5. 主控或具备项目决策能力的岗位依据证据作出 go/no-go 决策。
6. 未通过时带反馈重研；超过重研轮次后强制形成结论并记录理由。

验收：每个候选机会可追溯来源，每个简报可验证、可构建、可验收。

### 6.3 自主开发与验收

1. 主控根据产品简报调整组织、能力授权和岗位分配。
2. 具备工程与质量能力的岗位完成实现和自动化验证。
3. 独立验收岗位基于人格画像真实使用产品。
4. 体验报告驱动优先级和修复。
5. 达到验收标准后形成可发布版本。
6. 发布后持续观察指标，决定迭代或终止项目。

验收：交付物有代码、测试、体验报告和决策记录；失败项目有复盘和经验沉淀。

### 6.4 人类治理

1. 股东通过仪表盘观察组织、预算、项目和消息。
2. 管家解释状态、汇总报告并提供升级建议。
3. 升级事项包含背景、影响、选项和推荐理由。
4. 股东批准、拒绝或超时；超时默认拒绝。
5. 所有决策进入审计记录。

验收：股东可以不参与日常执行，但不会失去对关键动作的控制。

### 6.5 日常运营

- 股东按计划收到预算、用量、系统状态和待办报告。
- 公司按节奏形成日报、周报和组织复盘。
- 灾难、升级和定时报告按级别在仪表盘通知中心投递。
- 备份定期执行，并可按既定恢复目标恢复。

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 身份认证、最小权限、租户隔离、密钥保护、工具白名单、沙箱隔离、审计 |
| 可靠性 | 员工或 Runner 故障后任务可恢复；重复投递不产生重复业务副作用 |
| 数据一致性 | 消息、状态、计量和预算变更具有明确的一致性边界与幂等语义 |
| 可观测性 | OpenTelemetry + 可插拔 Profile；默认 local，Elastic Stack 可选；完整 Profile 提供指标、日志、APM、SLO、错误预算和告警 |
| 性能 | 长任务不阻塞控制面；调度、消息和模型调用具有独立超时与退避策略 |
| 可扩展性 | 组织与运行资源可以分离扩展，不因员工数量线性增加管理复杂度 |
| 可用性 | 仪表盘清晰展示公司状态、阻塞原因、升级事项和预算风险 |
| 可维护性 | 核心规则可测试，模型和工具可替换，设计变更可追踪 |
| 开放性 | 全链路开源并支持自托管；提供租户数据导出与校验迁移包，真实支付和跨环境导入后置 |
| 隐私与合规 | 明确数据保留、删除、导出和第三方模型数据处理边界 |

默认工程目标：控制面月度可用性 ≥99.5%，普通读 API P95 ≤300ms，普通写 API P95 ≤500ms，任务领取 P95 ≤2 秒，消息消费 P95 ≤10 秒，用量入账 P95 ≤60 秒，Outbox 投递和 RustFS 上传成功率 ≥99.5%。MVP 容量基线为单租户单机聚合 20 员工、40 并行任务、100 任务/小时、1000 消息/小时、100 模型请求/分钟、2 倍 15 分钟突发和 24 小时 soak。备份默认关闭；启用后全量目标 RPO 24 小时/RTO 8 小时，账本审计 15 分钟/4 小时，密钥库 15 分钟/2 小时。以上服务目标为默认门禁，备份目标仅对启用组件生效。

## 10. 分阶段验收

| 阶段 | 产品能力 | 验收标准 |
|---|---|---|

## 11. 风险与依赖

| 风险/依赖 | 影响 | 应对要求 |
|---|---|---|
| 模型能力与价格波动 | 产出质量、预算和模型策略不稳定 | 模型可替换，能力与成本持续评估 |
| 模型幻觉与提示注入 | 错误决策、越权动作、数据泄漏 | 证据校验、权限隔离、外部内容降权、审批 |
| 沙箱或容器逃逸 | 宿主和其他租户受影响 | 安全基线、最小权限、网络隔离、持续测试 |
| 跨租户泄漏 | 产品级安全事故 | 全链路租户作用域、隔离测试、审计 |
| 运营权限越界 | 提供方访问租户内容或执行未授权动作 | 独立运营身份、支持授权、最小权限、双人紧急访问和审计 |
| 预算超支 | 成本失控 | 调用前约束、实时计量、对账和硬性熔断 |
| Provider 限流或不可用 | 员工与管家停摆 | 超时、退避、降级和明确失败状态 |
| 真实支付与税务未确定 | 无法形成生产收费 | 本地套餐、配额和订阅账本已实现；真实渠道、价格、发票、税务和退款出现需求后再评审 |
| 自主开发质量不稳定 | 交付物不可用 | 自动化测试、独立体验、发布门禁和回滚 |
| 密钥备份与恢复复杂 | 数据不可恢复或密钥泄漏 | 明确密钥托管责任、加密备份和恢复演练 |
