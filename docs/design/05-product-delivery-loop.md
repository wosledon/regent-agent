# 05 产品交付与组织启动

- 版本：v0.1（待评审）
- 范围：组织启动、项目阶段门禁、Git/CI、体验验收、发布运行和终止复盘
- 对应缺口：G-13、G-14、G-15、G-16、G-28

## 1. 闭环目标

公司必须能够完成以下闭环，而不是只产出代码或报告：

```text
章程 -> 组织启动 -> 市场调研 -> 产品简报 -> go/no-go
     -> 开发 -> 自动化验证 -> 独立体验 -> 发布 -> 运行时观测
     -> 迭代或终止 -> 复盘与公司记忆
```

每个阶段都有明确输入、证据、负责人和退出条件。

## 2. 组织启动与动态岗位

### 2.1 启动期决策

公司启动时只创建主控，不创建预设 CEO 或固定岗位名单。

- 主控是编排运行时，初始状态为 `Unassigned`，不占编制。
- 主控读取 Charter 后为自己创建岗位，名称、职责、能力和模型档位由主控决定。
- 自建岗位通过策略校验并绑定 EmployeeRuntime 后，主控进入 `Active` 并占用一个编制槽。
- 主控再按能力缺口规划初始组织，可以合并或拆分岗位。
- 平台模板只提供可选能力包，不强制生成固定角色。

完整规则见 [06 主控与动态组织](./06-controller-and-organization.md)。

### 2.2 启动顺序

1. 创建公司和有效 Charter。
2. 控制面创建 `Controller(state=Unassigned)`。
3. 主控为自己创建岗位并绑定 EmployeeRuntime。
4. 主控根据当前目标授予或创建调研、产品定义等能力。
5. 调度器分配 Runner，员工进入 `Active`。
6. 具备相应能力的岗位执行调研和产品定义。
7. go 通过后，主控按交付、质量、独立验收和运行能力缺口调整组织。

### 2.3 启动期责任

| 对象 | 创建/决策者 | 约束 |
|---|---|---|
| 主控自建岗位 | 主控 | 控制面校验编制、预算、能力和禁止权限 |
| 初始组织计划 | 主控 | 必须覆盖当前阶段关键能力，不要求固定角色 |
| 技术评审 | 具备 `technical.review` 的非作者 | 不要求 CTO 名称 |
| 招聘与考核 | 具备 `employee.hire` / `employee.assess` 的岗位 | 不要求 HRBP 名称 |
| 独立验收 | 与实现者分离的验收岗位 | 不要求体验官名称 |

## 3. 项目阶段门禁

| 阶段 | 输入 | 必需证据 | 退出条件 | 决策者 |
|---|---|---|---|---|
| Proposed | Charter、市场信号 | 机会描述 | 进入调研 | 主控或 `project.decide` 岗位 |
| Researching | 候选问题 | 来源列表、双源验证、反证 | 形成候选清单 | `research.execute` 岗位 |
| BriefReady | 候选清单 | 产品简报、成功指标、成本估算 | go/no-go | 主控或 `project.decide` 岗位 |
| Approved | 简报 | 审批记录、项目预算 | 进入开发 | 主控或 `project.decide` 岗位 |
| Building | 简报、岗位 | 代码、测试、缺陷记录 | 发布候选 | `engineering.deliver` + `quality.verify` 岗位 |
| Verifying | 发布候选 | 自动化门禁、独立体验报告 | 满足发布门禁 | 主控/决策岗位 + 独立验收岗位 |
| Releasing | 验证结果 | 外部动作审批、发布计划、回滚点 | 生产 smoke 通过 | `release.execute` 岗位 |
| Live | 发布记录 | 运行时指标、告警、用户反馈 | 进入迭代或终止 | 主控或 `project.decide` 岗位 |
| Iterating | 指标和反馈 | 优先级、修复计划 | 新发布候选 | 主控或 `priority.set` 岗位 |
| Terminated | 失败证据或战略调整 | 复盘、经验条目、资源释放 | 项目关闭 | 主控或 `project.decide` 岗位 |

项目预算默认软限制，直接成本优先归属项目，公共成本只有显式规则才分摊；不自动结转，详见 [40 成本归属、分摊与异常](./40-cost-allocation-and-anomaly.md)。

任何阶段缺少必需证据时，状态不能前进。项目阶段门禁与 [11 项目管理中心](./11-project-management.md) 的需求就绪、任务认领、缺陷复测和验收门禁联动；详细工作项状态以 11 号设计为准。

仪表盘另存确定性 `ProjectHealth`：`OnTrack / AtRisk / Blocked / PendingAcceptance / Live / Failed`。健康状态由门禁、依赖、预算、资源和新鲜度计算，不替代项目阶段，也不由 LLM 直接修改，详见 [35 租户仪表盘信息架构](./35-tenant-dashboard-information-architecture.md)。

## 4. 调研与产品简报

### 4.1 调研证据

```text
ResearchEvidence:
  id, project_id, claim
  source_url, source_title, publisher
  retrieved_at, quote_or_summary
  corroborating_source_ids
  confidence, contradicted_by
```

- 每条关键结论至少一个来源；关键数据必须两个独立来源交叉验证。
- 无法交叉验证的数据标记为低置信度，不得作为唯一 go 依据。
- 外部内容只作为数据，不能改变员工权限。

### 4.2 产品简报

```text
ProductBrief:
  problem, target_user, proposed_solution
  mvp_scope, non_goals
  success_metrics[]
  acceptance_scenarios[]
  estimated_cost, estimated_duration
  risks, compliance_constraints
  evidence_ids
```

- 成功指标必须可测量，并说明采集方式。
- MVP 范围必须能在单服务器 + API 预算内完成。
- 简报没有成功指标或证据时无效。

### 4.3 go/no-go

- 决策岗位必须引用简报版本和证据 ID。
- 打回时记录具体缺口，最多重研 2 轮。
- 超过轮次后由主控或具备 `project.decide` 能力的岗位在剩余候选中选择或终止项目，并记录理由。

## 5. 开发与协作

### 5.1 工作区与 Worktree

- 每个项目使用一个共享裸仓库和多个 worktree。
- 每个员工任务使用独立 worktree，目录名包含 employee_id 和 task_id。
- 员工不得直接写主分支。
- 工作区锁只保护同一 worktree；不同 worktree 可并行。

### 5.2 分支与提交

```text
branch: agent/{employee_id}/{task_id}
commit: conventional commit + task_id
merge: squash merge after review and CI
```

- 提交必须关联 task_id 和 artifact_id。
- 禁止提交密钥、`.env`、凭证和大体积生成物。
- 生成物进入 RustFS，仓库和 Postgres 只保留清单、引用和哈希。

### 5.3 评审与合并

- 作者不能成为自己变更的唯一批准者。
- 至少一名具备 `technical.review` 能力的非作者批准，并满足版本化评审规则。
- CI 未通过时禁止合并。
- 冲突由任务员工解决；无法解决时升级给具备技术决策能力的岗位。
- 合并后主分支生成新的不可变 commit 和构建号。

## 6. CI 与质量门禁

发布候选必须通过：

1. 还原依赖和编译。
2. 单元测试与关键集成测试。
3. 静态检查、密钥扫描和依赖漏洞扫描。
4. 容器构建与镜像扫描。
5. 契约测试和基础端到端测试。
6. 生成测试报告、SBOM、镜像摘要、签名和发布包。

测试失败时进入 `Building`，缺陷关联任务和代码提交。测试报告不可由开发员工手工改写。

## 7. 独立体验验收

### 7.1 人格与独立性

- 具备 `product.define` 能力的岗位从简报导出 2～3 个独立人格画像。
- 独立验收岗位不读取开发组的自我评价，只读取产品、用户目标和验收场景。
- 人格画像目标不同、熟练度不同，使用隔离浏览器配置。

### 7.2 执行协议

1. 启动隔离的发布候选运行时。
2. 独立验收岗位按真实目标使用 Playwright 操作产品。
3. 记录步骤、结果、卡点、困惑、放弃、留存和付费意愿。
4. 对照简报中的成功指标评分。
5. 生成体验报告和证据附件。
6. 主控或具备 `priority.set` 能力的岗位确定优先级，开发修复后复测对比。

### 7.3 通过规则

- 具体量化门槛在项目简报中定义，不允许验收时临时降低；项目只能提高门槛。
- 三个画像在同一关键环节全部失败视为 P0，项目不得发布。
- 阻断级安全、数据丢失、隐私或越权问题一票否决。
- 复测必须引用上一轮报告，明确修复项和新增回归。
- AI 人格验收不能替代真实用户验证。

| 指标 | 初始门槛 |
|---|---:|
| 验收证据完整率 | 100% |
| 关键场景通过率 | 100% |
| 总体场景通过率 | ≥80% |
| 未关闭 P0/P1 | 0 |
| 完成核心目标的人格数 | 至少 2/3；只有 2 人格时须全部完成 |
| 无效步骤率 | ≤10% |
| 误操作 | 每任务平均 ≤1 次 |
| 非计划求助 | 每任务平均 ≤1 次 |
| 错误自行恢复率 | ≥80% |
| 关键可访问性检查 | 100% |
| 可遗留 P2 | ≤3，且不影响核心流程 |

环境故障单独记录，不能算作产品成功或产品失败。任务耗时以简报目标为准；没有目标时首版只记录基线。

### 7.4 设计合理性评分

每个维度使用 1～5 分，并附页面、步骤、截图或录屏证据：

| 维度 | 评价内容 |
|---|---|
| 信息架构 | 入口、信息和功能是否容易找到 |
| 心智模型 | 页面结构是否符合用户预期 |
| 流程合理性 | 步骤是否必要，顺序是否符合目标 |
| 反馈与状态 | 是否清楚当前状态和操作结果 |
| 错误预防与恢复 | 是否容易误操作，出错后能否恢复 |
| 一致性 | 术语、按钮、交互和视觉是否统一 |
| 视觉层级 | 重点是否突出，信息是否过载 |
| 可访问性 | 键盘、标签、对比度、焦点和读屏 |
| 性能感受 | 加载、响应和等待是否可接受 |
| 信任感 | 数据、权限、费用和风险是否清楚 |

通过条件：平均分 ≥4，且任何维度不得低于 3。关键设计缺陷必须定为 P0 或 P1，不能只扣分。

发现类型分为 `FunctionalFinding`、`UsabilityFinding`、`DesignFinding` 和 `AccessibilityFinding`。

### 7.5 复测规则

```text
首轮验收
  → 修复 P0/P1 和指定 P2
  → 复测所有失败场景
  → 回归全部关键场景
  → 最多再进行 2 轮复测
```

- 每轮必须展示已修复、仍失败和新增回归。
- 不能降低标准、删除失败场景或修改人格来通过。
- 连续两轮复测不达标，项目进入终止或重新规划。
- 新发布候选重新开始完整验收轮次。

结论只能是 `Pass`、`ConditionalPass`、`Fail`、`Blocked` 或 `TerminateCandidate`。

## 8. 发布与运行时

### 8.1 发布门禁

发布前必须满足：

- 自动化门禁通过。
- 独立体验门禁通过。
- 发布审批已绑定版本 Tag、本地镜像 ID、环境和参数。
- ReleaseManifest 固定版本 Tag、源 commit、基础镜像 digest、schema 和兼容版本。
- 数据库迁移采用 Expand/Deploy/Contract，并明确应用回滚边界。
- 运行时密钥、域名、TLS 和监控已配置；备份按 BackupProfile 可选启用。
- 回滚点已验证。
- RightsDeclaration 有效，UnknownRights 不得发布。
- ThirdPartyNotice、SBOM、许可证、秘密、PII 和内容安全检查通过。
- 公开发布包含 LICENSE、NOTICE 和 ReleaseLicenseReport，未知许可证为 0。

### 8.2 产品运行时

产品运行时与员工容器分开配额，使用独立项目命名空间。运行时必须具备：

- 健康检查、日志、指标和追踪。
- 资源限制和租户网络隔离。
- 数据备份和恢复方案。
- 密钥注入机制，不进入镜像或仓库。
- 发布版本和配置版本标记。

### 8.3 发布后动作

1. 部署并执行 smoke test。
2. 校验核心成功指标可采集。
3. 观察 30 分钟默认观察期。
4. 无异常进入 `Live`；异常回滚或进入 `Building`。
5. 将发布、回滚和指标写入公司志。

外部发布属于 C 级动作，必须通过升级审批；生产数据删除属于 D 级动作。

## 9. 迭代、终止与复盘

### 9.1 迭代触发

- 成功指标下降。
- 体验报告出现重复阻断问题。
- 用户反馈或运行时错误超过简报阈值。
- 成本超过项目预算。
- 市场证据发生变化。

### 9.2 终止条件

- 连续两轮复测仍未达到简报门槛。
- 成本超过硬预算且股东拒绝调整。
- 产品触碰能力边界或伦理红线。
- 主控或具备 `project.decide` 能力的岗位依据证据判断机会不再成立。

### 9.3 复盘

终止项目必须记录：

- 原假设与证据。
- 关键决策和时间线。
- 成功与失败因素。
- 成本与资源消耗。
- 可复用经验和明确不再尝试的做法。

复盘进入公司记忆；项目终止不终止公司使命。

## 10. 能力职责摘要

| 能力 | 主要责任 | 边界 |
|---|---|---|
| 主控编排 | 组织规划、任务创建、优先级和闭环推进 | 不能替代股东升级审批 |
| `research.execute` | 多源调研、证据和候选清单 | 不能替代产品定义 |
| `product.define` | 简报、成功指标、体验人格 | 不能替代开发自评 |
| `technical.review` | 技术方案、评审规则和非作者评审 | 不能替代独立验收 |
| `employee.hire` / `employee.assess` | JD、面试、考核和编制执行 | 不能替代股东预算审批 |
| `engineering.deliver` / `quality.verify` | 实现、自动化验证、缺陷修复 | 不能替代独立验收 |
| `experience.validate` | 独立真实使用和体验报告 | 必须与实现者分离 |
| `release.execute` / `runtime.operate` | 发布、回滚、运行时管理 | 不能替代对外动作审批 |
| 管家 | 只读解释、报告、升级建议 | 不是公司员工 |

## 11. 交付闭环验收

1. 公司启动时先创建主控，由主控自建岗位并规划初始组织，不依赖固定 HRBP/CTO。
2. 每个项目阶段可以展示进入和退出证据。
3. 产品简报缺少成功指标时无法进入 Approved。
4. 两个员工可以并行开发而不覆盖同一 worktree。
5. 作者无法单独批准并合并自己的变更。
6. CI 失败时无法形成发布候选。
7. 三个体验画像同时流失时项目无法发布。
8. 发布审批与镜像摘要、环境和参数绑定。
9. 发布失败可以回滚到已验证版本。
10. 运行时指标可以驱动下一轮迭代。
11. 终止项目必须产生复盘和公司记忆条目。
12. 验收报告同时包含功能、易用性、设计合理性和可访问性发现。
13. 关键场景未全部通过时不得发布。
14. 未关闭 P0/P1 或设计维度低于 3 时不得发布。
15. 复测保留失败场景并回归全部关键场景。
16. 连续两轮复测失败后进入终止或重新规划。
17. 环境故障与产品失败分开记录。
18. AI 人格验收不会被标记为真实用户验证。

### 11.1 统一完成标准

- 通用 Done 要求成果、验证、阻断问题、依赖、成本和审计完整。
- 开发、测试、调研、需求、里程碑和缺陷使用各自附加标准。
- 执行者提交，验证者检查，控制面关闭；执行者不能自关闭。
- DoneEvidence 保存验收、Artifact、测试、评审、安全检查、缺陷、成本、审计和验证者。
- 安全、租户隔离、密钥保护和审计不可豁免，其他豁免必须限期并审批。

## 12. MVP 边界与退出

### 12.1 里程碑 A：公司成立

- 主控从 `Unassigned` 自建岗位并进入 `Active`。
- 自主创建初始员工岗位并分配能力。
- 产出带来源、可构建、含成功指标的产品简报。
- 无需 Boss 设计固定岗位。

### 12.2 MVP：自主交付

MVP 为单租户、自托管可运行的完整闭环：

```text
Charter → 组织 → 简报 → 项目/需求/任务 → 加权认领
→ 开发/测试 → 缺陷修复 → 独立验收 → 发布候选 → 复盘/记忆
```

退出条件：

1. 空白环境启动到 Active 组织 ≤15 分钟。
2. 产品简报产出 ≤4 小时。
3. 至少 3 次端到端尝试，其中 2 次形成独立验收通过的发布候选。
4. 关键场景 100% 通过，P0/P1 清零。
5. 发布失败能回滚到已验证版本。
6. Runner 崩溃或重启不丢任务、成果和账本。
7. 所有模型调用有预算预留和用量入账。
8. 硬预算、租户隔离和密钥边界测试通过。
9. 备份可以实际恢复。
10. Boss 只处理升级事项，不参与日常派工。
11. 关键决策、成本和组织变更可审计。
12. 失败项目能形成复盘并沉淀经验。

### 12.3 后置能力

在线支付、完整运营平台、多租户商业化、一键安装包、高级图谱、自动招聘评分平台、自动绩效处罚、技能市场、SAML 和完整 Butler 报告不在首个 MVP 内；OIDC 企业登录按 Q-028 提前。
12. 从调研到发布的每个关键动作都能追溯到任务、员工、成果和审计事件。
13. 招聘并发占用同一空槽时只有一个候选人可录用。
14. 面试评分、实操证据和最终决策可追溯。
15. 记忆条目可以追溯来源、租户、项目和最后验证时间。
16. 低置信度或被注入污染的记忆不能自动提升为高权限指令。
17. 项目终止后资源释放与记忆沉淀均完成。
18. 主控自建岗位、组织变更、JD 和评分标准都有版本记录。
19. 修改岗位名称不会改变权限、调度或审计关联。
20. 主控无继任者时不能关闭自建岗位后让公司继续自主运行。
21. 租户 token 不能访问运营平台，运营人员无 SupportGrant 不能读取租户业务数据。
22. 暂停租户后新任务和新模型调用被拒绝，备份和导出仍可按授权执行。
23. 产品发布前已完成运营监控、状态页、备份和回滚演练。
24. 发布必须固定版本 Tag、记录本地镜像 ID，并通过 Expand/Deploy/Contract 兼容检查。
25. 发布必须通过安全、容量、混沌和升级测试；恢复测试仅对启用备份组件要求。
26. elastic Profile 下关键链路必须在 Kibana 中具有指标、日志和 APM 追踪；local/off Profile 不要求该门禁。
27. 工具、MCP、Skill、依赖和镜像必须具有 digest、签名、SBOM 和准入记录。
28. 对外发布必须通过内容安全门禁，红线内容不得发布。
29. 对外发布必须具有有效权利声明和完整第三方通知，UnknownRights 不得发布。
30. 招聘必须完成岗位相关盲评、FairnessAudit 和申诉窗口，能力门槛不得降低。
31. 公开发布必须通过 Apache-2.0、NOTICE、SBOM 和第三方许可门禁。

### 11.1 运营就绪门禁

托管产品发布前必须满足：

- 租户账户、套餐、配额和订阅可在运营平台管理。
- Runner/Gateway 资源池、部署版本和 drain 可用。
- 事件、状态页、值班和脱敏通知可用。
- SupportGrant、紧急访问和运营审计可用。
- 备份作业、恢复审批和演练报告可用。
- 租户控制面与运营平台身份、API 和数据库访问边界通过测试。

## 12. 招聘与面试流水线

### 12.1 招聘状态

```text
Draft -> Open -> Interviewing -> Offered -> PendingBossApproval -> Hired
                    |  \-> Rejected -> Appealed -> Interviewing / Rejected
                    \-> RetryWithDifferentModel
Open -> Frozen / Closed
```

- 招聘开始时原子占用一个空槽。
- 主控可决定不录用；正向录用必须先经 Boss 批准。
- 录用时把岗位置为 `Filled`，员工进入 `Pending` 或 `Active`。
- 拒绝、冻结和关闭都会释放对应招聘占用。
- 拒绝进入 Appealed 时暂缓释放，申诉结束或超时才完成淘汰。
- 同一岗位并发录用使用行锁或条件更新，防止超编。

### 12.2 面试流程

1. 具备招聘能力的岗位生成 JD、题库和评分标准；具备 `technical.review` 能力的非作者评审技术项。
2. 发布 FairnessPolicy，固定岗位相关标准、盲评规则、等价案例和门槛。
3. 笔试在隔离环境执行，自动评分。
4. 实操使用一次性容器和真实任务，不访问生产工作区。
5. 评分记录包含模型版本、提示模板、评分表版本和原始 artifact。
6. 完成独立评分、FairnessAudit 和阻断性 BiasFinding 处理。
7. 主控可决定淘汰；录用、降配录用和换模型重试提交 Boss 最终批准。
8. 拒绝必须提供证据和原因，候选人可申诉、复测或申请合理便利。
9. 面试记录进入授权审计，不进入普通公共知识，不包含密钥。

### 12.3 评分与模型迁移

- 评分维度在面试前固定，不允许看到结果后修改。
- 产出证据优先于口头汇报。
- 降配录用必须记录能力缺口和后续补强任务。
- 模型换岗需要 benchmark 或产出数据支持，不能由单次面试决定。
- 试用期结束由具备 `employee.assess` 能力的岗位根据交付物和成本证据决定转正、继续试用或淘汰。

## 13. 项目复盘与记忆

- 项目终止时必须生成 Reflection 记忆候选，包含原假设、证据、决策时间线、成本、成功因素和失败因素。
- 候选先进入个人或项目范围，经过策展后可沿组织树向上提名为组织记忆或知识库资产。
- 项目终止后相关记忆降低默认检索权重，但不立即删除。
- 被提示注入、错误或合规风险污染的记忆可以隔离，并保留审计。
- 个人记忆、组织记忆、知识库、RAG、图谱多跳、遗忘和删除传播的统一模型见 [09 记忆系统](./09-memory-system.md)。
