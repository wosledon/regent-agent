# 44 容量与性能基线

- 版本：v0.1（待评审）
- 范围：单机聚合容量、API 延迟、队列上限、背压、租户公平和容量门禁
- 对应需求：FR-088、BR-152、BR-153、BR-154、BR-155
- 对应缺口：G-59

## 1. 范围

- 当前只承诺单租户、单机部署的聚合容量。
- 不承诺大规模多租户 SaaS 容量。
- 多租户公平性测试最多使用 5 个模拟租户。
- 参考硬件为现有 12 核、30G 内存、NVMe 单机基线。

容量数字是整个部署的聚合上限，不是每个租户分别叠加。

## 2. 容量基线

| 项目 | 目标 |
|---|---:|
| 自托管活跃租户 | 1 |
| 活跃员工 | 20 |
| 最大并行 TaskRun | 40 |
| 任务创建 | 100/小时 |
| 消息 | 1000/小时 |
| 模型请求 | 100/分钟 |
| 突发 | 2 倍持续 15 分钟 |
| 稳定性 | 24 小时 soak |
| 公平性测试租户 | 最多 5 个模拟租户 |

Provider 使用可编排模拟服务，覆盖正常、流式中断、429、5xx、高延迟和超长上下文。

## 3. API 性能

| 接口或路径 | P95 目标 |
|---|---:|
| 普通读 API | ≤300ms |
| 普通写 API | ≤500ms |
| 任务领取 | ≤2 秒 |
| 消息消费 | ≤10 秒 |
| 用量入账 | ≤60 秒 |
| 仪表盘实时状态 | ≤5 秒 |
| RustFS 上传 | ≤10 秒，50MB 以内 |
| 控制面 API 月度可用性 | ≥99.5% |

不计入普通 API 延迟：

- Provider 推理。
- 长工具执行。
- 大文件上传。
- 跨公网调用。
- 用户审批等待。

Provider 可用性单独统计，不混入 Regent-Agent 自身 API 可用性。

## 4. 队列上限与背压

| 队列 | 默认上限 | 超限行为 |
|---|---:|---|
| 单租户 Pending Task | 200 | 拒绝新任务，返回 429 |
| 单员工待认领/待处理项 | 20 | 停止新派工 |
| 单租户消息积压 | 5000 | 限流并提示重试 |
| Outbox 待投递 | 10000 | 告警并限流非关键写入 |
| 模型在途请求 | 全局 40 | 排队或返回 429 |
| 单租户模型在途请求 | 10 | 排队或返回 429 |
| 单员工模型在途请求 | 2 | 排队或返回 429 |

规则：

- 队列满时不能静默丢弃。
- 超限响应包含原因和 `Retry-After`。
- 已接受消息必须保留并可重放。
- 任务创建幂等键必须保留，重试不生成重复任务。
- 关键安全事件和 L3 告警有保留容量，不被普通消息挤掉。
- 队列阈值和上限版本化，变更写入审计。

## 5. 租户公平

- 共享 Runner 使用租户加权轮询。
- 单租户连续占用共享槽位最多 3 次，然后必须让出等待租户。
- 单租户不能占满全部共享重任务槽。
- 模型请求、数据库连接、沙箱和存储均有租户级配额。
- 资格检查先于配额，不能让无能力任务占用槽位。
- 公平调度不绕过能力、权限、WIP、预算和优先级。

## 6. Noisy Neighbor 门禁

在单租户持续压测、其他租户存在合格工作时：

| 指标 | 门槛 |
|---|---:|
| 其他租户普通 API P95 劣化 | ≤20% |
| 其他租户合格任务最大等待 | ≤30 秒 |
| 跨租户数据或密钥访问 | 0 |
| 任务、消息或账本丢失 | 0 |

- 压测租户不得通过提高自身优先级绕过配额。
- 其他租户的 L3/SEV1 保留应急容量。
- 公平性测试记录每个租户的吞吐、等待、错误和资源使用。

## 7. 资源约束

- 沙箱 CPU、内存、PID、磁盘和网络按任务限制。
- Postgres 设置连接池、语句超时和锁超时。
- RustFS 上传使用有界并发和可恢复 PendingUpload。
- 日志按大小和时间轮转。
- 指标标签不得使用高基数 task_id、employee_id 或 request_id。
- 资源不足时限流、暂停新任务或触发扩容评估，不能无限排队。

## 8. 突发与 soak

### 8.1 突发

- 在基线上施加 2 倍负载，持续 15 分钟。
- 覆盖任务、消息、API 和模型请求。
- 验证背压、幂等、租约和队列恢复。
- 突发结束后队列必须在 5 分钟内回到正常水位。

### 8.2 Soak

- 连续运行 24 小时。
- 无任务、消息或账本丢失。
- 无重复认领、重复入账或无限重试。
- 内存、连接、磁盘和队列无不可恢复的持续增长。
- 资源使用保持在目标硬件内。

## 9. 容量测试流程

```text
准备模拟 Provider 和确定性负载
  → 预热
  → 基线负载
  → 2 倍突发 15 分钟
  → 单租户 noisy neighbor 压测
  → 24 小时 soak
  → 校验 SLO、队列、资源和数据一致性
  → 生成 CapacityReport
```

- CI 运行短容量冒烟。
- 发布前运行完整容量测试。
- 容量报告绑定版本 Tag、硬件、配置和测试数据版本。
- 不使用真实 Provider 作为容量测试前提。

## 10. CapacityReport

```text
id, version_tag, source_commit
hardware_profile
test_profile
started_at, completed_at
load_profile
api_latency
queue_high_watermarks
tenant_fairness
resource_usage
data_integrity
result, evidence_refs
```

- 未通过容量门禁不得发布。
- 例外必须有负责人、补偿控制、到期时间和审批。
- 历史报告不可静默覆盖。

## 11. 指标

| 指标 | 目标 |
|---|---:|
| 队列静默丢弃数 | 0 |
| 普通读/写 API P95 | 300ms / 500ms |
| 突发恢复时间 | ≤5 分钟 |
| Noisy Neighbor API 劣化 | ≤20% |
| Noisy Neighbor 最大等待 | ≤30 秒 |
| 24 小时数据丢失 | 0 |
| 未通过容量门禁发布数 | 0 |

## 12. 测试场景

1. 20 员工、40 并行 TaskRun 负载通过。
2. 100 任务/小时和 1000 消息/小时负载通过。
3. 100 模型请求/分钟负载通过。
4. 2 倍突发持续 15 分钟不丢数据。
5. Pending Task 达到 200 时返回 429。
6. 员工待处理项达到 20 时停止派工。
7. 消息积压达到 5000 时限流。
8. Outbox 达到 10000 时告警并限流。
9. 模型在途请求按全局、租户和员工上限排队。
10. 队列满时不静默丢弃。
11. 重试使用原幂等键且不重复。
12. 单租户连续占用共享槽 3 次后让出。
13. 单租户压测时其他租户 API P95 劣化不超过 20%。
14. 其他租户合格任务等待不超过 30 秒。
15. L3/SEV1 在拥塞时仍有保留容量。
16. 24 小时 soak 无任务、消息或账本丢失。
17. 内存、连接和队列无不可恢复增长。
18. Provider 故障不污染 Regent API 可用性统计。
19. 容量报告绑定版本和硬件。
20. 未通过容量门禁时发布失败。

## 13. 验收场景

1. 当前只承诺单租户单机聚合容量。
2. API P95 和既有 SLO 可复现。
3. 所有队列有上限、背压和明确错误。
4. 租户公平和 noisy neighbor 门槛可测试。
5. 突发和 24 小时 soak 无数据丢失。
6. 大规模多租户容量不作为当前承诺。
