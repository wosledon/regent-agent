# 10 绩效与自我改进

- 版本：v0.1（待评审）
- 范围：员工自驱动、KPI、绩效评估、组织动作、反作弊、申诉与审计
- 对应需求：FR-040、FR-075、BR-030、BR-106、BR-107、BR-108、BR-109
- 对应缺口：G-27、G-46

## 1. 定位

每名员工都具备一定的自驱动能力，不只主控会优化组织，开发也会优化开发流程，测试会优化测试流程，验收会优化体验流程。

绩效系统负责把“主动改进”和“绩效评估”结合起来：

```text
工作 → 证据 → 自评 → 复核 → 绩效动作 → 下一周期验证
```

KPI 是证据信号，不直接等于自动解雇。

## 2. 核心不变量

1. 所有员工都可以提出自我改进，但不能自行扩大权限。
2. KPI 必须基于控制面事实，不能只靠员工汇报。
3. 员工不能评估自己并直接执行奖惩。
4. KPI 不达标不直接触发解雇。
5. 高影响动作需要充分证据、独立 AI 复核、申诉和审计；只有解雇需要人类事前批准。
6. 评估者由能力决定，不要求 HRBP 岗位名称。
7. 主控不能在无继任者时被解雇。
8. 绩效动作必须区分人的问题、流程问题、模型问题和资源问题。
9. 指标必须防止刷分、隐藏失败和降低标准。
10. 所有绩效定义、快照、评估和动作按租户隔离。
11. 非解雇绩效动作由 Controller/AI 自主决定，不需要人类事前批准。
12. 解雇、移除模型订阅和释放编制必须由人类 Boss 最终批准。
13. 人类只参与解雇和事后审查，不参与其他日常绩效动作。

## 3. 员工自驱动循环

```text
执行任务
  → 收集结果、成本和反馈
  → 自我反思
  → 生成改进提案
  → 在授权范围内审批
  → 应用改进
  → 下一周期验证
```

员工可以提出：

- 工作流改进。
- 任务拆解方式。
- 提示和指令优化。
- 工具使用优化。
- 技能和知识补充。
- 模型档位调整。
- 岗位职责调整。
- 协作方式改进。
- 组织能力缺口。

权限边界：

- 开发可以优化个人开发流程。
- 不能自行修改公司组织树。
- 主控可以规划组织。
- 不能绕过 Boss 升级审批。
- 工作流、记忆和 KPI 改进不能提升 Tool 权限。

## 4. 改进提案

```text
ImprovementProposal:
  id, tenant_id, employee_id
  proposal_type
  problem_statement
  evidence_refs[]
  proposed_change
  expected_benefit
  scope_type: personal | organization
  scope_position_id?
  status, reviewer_id?, created_at
```

提案类型：

- `workflow`
- `skill`
- `tool_usage`
- `model`
- `position`
- `organization`
- `kpi`
- `knowledge`

个人范围提案由作者自行试点；组织范围沿组织树向上审查。

技能自我进化流程：

```text
个人技能草稿 → 自测与回归 → ImprovementProposal
→ 能力负责人审查 → 小范围试点 → 发布组织技能版本
→ 其他员工按需安装 → 持续度量与升级
```

- 员工不能修改平台 SystemPrompt、公共技能旧版本或权限。
- 公共技能保留作者、来源、评测、试点和版本记录。
- 安装技能不自动授予 Capability 或 Tool。
- 跨租户公共资产需要脱敏、匿名化、许可证和平台审核。

## 6. KPI 维度

### 6.1 通用维度

- 交付质量。

- 协作质量。

- 公司里程碑完成率。

- 组织能力缺口。

- 缺陷逃逸率。
- CI 首次通过率。
- 返工率。
- 代码评审问题。
- 单任务成本。

### 6.4 测试

- 缺陷发现率。
- 自动化覆盖率。
- 误报率。
- 回归遗漏率。
- 测试周期。
- 测试流程改进贡献。

### 6.5 考核岗位

- 招聘周期。
- 面试评分准确性。
- 新员工试用通过率。
- 考核校准质量。
- 错误降职或解雇率。

### 6.6 工具画像与角色漂移

- Primary Tool 使用率。
- Auxiliary Tool 使用率。
- Restricted 激活申请和拒绝率。
- 非本岗位核心工具使用占比。
- 角色漂移率：员工长期主要执行非本岗位核心工作。

架构师可以写代码，但如果长期主要编码而架构设计贡献不足，应触发岗位或流程复核，而不是直接判定绩效失败。

### 6.8 样本与目标校准

- 员工单周期至少 5 个完成任务或 2 周数据，否则标记样本不足。
- 效率类指标首月建立基线，再锁定目标。
- 高影响绩效动作至少参考 4 周趋势和独立证据。
- 安全和 P0 问题不受样本量限制。
- 目标值按岗位和项目模板配置，只能提高质量门槛，不能降低安全门槛。

### 6.9 任务加权与能力评分

任务复杂度按技术不确定性、需求歧义、影响范围、风险、协作和环境难度评分，映射为 `1 / 2 / 3 / 5 / 8`。权重在 Ready 前锁定，员工不能自评；拆分任务不得增加总权重。

```text
WeightedScore = TaskWeight × QualityFactor × CapabilityFitFactor
```

| 结果 | QualityFactor | CapabilityFitFactor |
|---|---:|---:|
| 一次验收通过 | 1.0 | 满足要求 1.0，超出两档以上 1.1 |
| 少量返工后通过 | 0.8 | 同上 |
| 重大返工后通过 | 0.5 | 同上 |
| 未通过或质量事故 | 0 | 不适用 |

- 单个任务最多占周期加权总量 30%。
- 能力不足必须拒绝认领、配置搭档或批准 stretch task。
- 加权得分不能抵消返工、缺陷、失误或安全事件。

```text
EffectiveCapability =
  40% 模型维度评分
+ 35% 历史任务表现
+ 15% 工具链适配
+ 10% 上下文与技能适配
```

能力维度包括编码、调试、测试、架构、系统设计、产品分析、调研、体验评审、写作、工具使用、长上下文、指令遵循和安全。模型 benchmark 必须版本化并带置信度，不能由员工自行修改。

### 6.10 任务类型与工作台账

TaskTypeDefinition 决定能力、Tool Profile、权重、Done、证据和 KPI。开发、测试、评审、对抗、裁决、验收、发布、招聘和知识沉淀分别统计。

EmployeeWorkLedger 记录任务类型、权重、核心/辅助关系、质量、能力匹配、加权得分、成本、时长和证据。按类型统计一次通过率、返工率、评审漏检率、裁决推翻率、对抗发现率和岗位匹配度。

同一成果只能有一个主任务权重，父子和协作任务不得重复计分；普通聊天不自动成为任务。

### 6.11 运行状态与归因

员工可用率、疲惫率、故障率、恢复时间和反复异常进入 KPI。状态事件必须记录 `reason_code` 和归因：

- 员工相关：无效循环、重复错误、参数错误、可避免过载。
- 平台/模型相关：Provider 5xx、Runner 故障、平台网络、模型不可用。
- 管理相关：WIP 过高、难度误判、未启用备份却宣称有恢复能力、长期超载。

只有员工相关且可避免的问题进入员工绩效；归因不明时待复核，状态异常不自动触发处罚。

- 员工可用率以 WorkSchedule 和 HolidayCalendar 定义的应工作时间为分母。
- 用户禁用窗口、休息和假期休眠不扣绩效，允许的夜间工作时间同等计入。
- 紧急唤醒单独归因，管理排班、平台故障和员工可避免问题分开统计。

## 8. 评估节奏

### 8.1 周期评估

- 主控默认 7 天。
- 其他员工按岗位配置。
- 周期、时区和截止时间存 KpiDefinition。

### 8.2 事件触发

- 连续多次任务失败。
- 严重质量或安全事件。
- 预算异常。
- 项目里程碑结束。
- 独立验收失败。
- 员工主动申请复核。
- 模型或岗位发生重大变化。

### 8.3 最小样本

- 样本不足时不得做高置信度结论。
- 结论必须带 confidence 和 evidence bundle。
- 长期低样本岗位延长观察期。

## 9. 评估流程

```text
周期或事件触发
  → 计算 KPI Snapshot
  → 汇总证据
  → 员工自评
  → 评估者复核
  → 生成绩效结论
  → 决策组织动作
  → 执行与审计
  → 下一周期验证
```

状态：

```text
Scheduled → CollectingEvidence → SelfAssessment → ReviewerAssessment
  → DecisionPending → Completed
  → Appealed → UnderReview → Completed
```

- 自评不能修改原始 KPI。
- 评估者不能删除反证。
- 结论必须引用证据。
- 动作执行使用独立权限。

## 10. 绩效动作

| 动作 | 说明 | 典型权限 |
|---|---|---|
| Retain | 保持现状 | `employee.assess` |
| Coach | 辅导、补知识、调整任务 | `employee.assess` |
| ImproveWorkflow | 优化流程或协作 | `workflow.review` |
| ChangeModel | 调整模型档位 | 预算与岗位权限 |
| GrantCapability | 授予新能力 | 能力管理权限 |
| Reassign | 调岗 | `org.design` |
| Demote | 降职或缩减职责 | `org.design` + 独立 AI 复核，无人类事前批准 |
| Freeze | 绩效冻结、暂停新任务 | `employee.assess` + 独立 AI 复核，无人类事前批准 |
| Terminate | 解雇、移除订阅和释放编制 | AI 提名 + 独立复核 + 申诉 + 人类 Boss 批准 |
| Escalate | 提交 Boss 决策 | 升级队列 |

高影响动作：

- 需要充分证据和原因归因。
- 需要非原评估者执行独立 AI 复核。
- 需要员工申诉窗口和完整审计。
- 降职和绩效冻结由 Controller/AI 自主执行，不等待人类事前批准。
- 申诉期间暂停尚未执行的高影响动作；已执行动作进入复核和纠正。
- 所有 Terminate 和移除订阅必须由人类 Boss 最终批准。
- 主控 Terminate 必须先完成继任。
- 统一评级持续很低时先进入 PendingRemovalQueue，完成归因、独立复核和申诉后再提交 Boss。

`approval_kind` 使用 `IndependentAIReview` 或 `HumanTerminationApproval`。后者必须绑定真实人类账户和不可变证据摘要。

## 11. 区分问题来源

绩效低下不能直接归因于员工。评估必须区分：

- 能力问题。
- 模型档位问题。
- 工作流问题。
- 需求质量问题。
- 工具或资源不足。
- 协作问题。
- 外部依赖。
- 指标设计问题。

优先尝试低成本改进，再考虑调岗或解雇。

## 12. 反作弊

防止员工刷 KPI：

- 不只接简单任务。
- 不隐藏失败。
- 不降低测试标准。
- 不虚报成本。
- 不批量制造低质量工作流。
- 不通过删除记忆隐藏错误。

控制措施：

- 平衡指标。
- 质量门槛。
- 独立验收。
- 成本约束。
- 同行评审。
- 反证记录。
- 长期趋势。
- 异常波动检测。

## 13. 申诉

- 员工可对结论和动作提出申诉。
- 申诉期间高影响动作暂停执行。
- 由非原评估者复核。
- 复核可以维持、修改或撤销动作。
- 所有申诉和结果进入审计。
- 错误绩效动作率进入主控 KPI。

### 13.1 人类事后审查

- 人类可审查降职、绩效冻结、解雇和其他高影响绩效动作。
- 事后审查不阻塞非解雇动作，不构成日常事前审批。
- 人类可调取完整证据、推翻结论、要求恢复权限、撤销动作或发起独立调查。
- 审查结果写入 HumanPerformanceReview，并生成纠正任务。
- 人类审查不能删除原始证据、申诉和动作历史。
- 解雇除事前人类批准外，同样接受事后审查。

## 14. 评估者约束

- 不能评估自己。
- 不能修改原始 KPI。
- 不能删除反证。
- 不能同时充当唯一审批者和执行者。
- 评估者本身也接受 KPI 考核。
- 利益冲突时重新分派评估者。

## 16. 调度与运行时

- 周期评估由调度器触发。
- 事件评估由 Outbox 事件触发。
- KPI 计算是确定性程序，不受 LLM 主观修改。
- LLM 只生成证据摘要、自评建议和动作建议。
- 评估任务使用普通 Task、租约和幂等机制。
- 主控默认 7 天周期可配置，其他员工按岗位周期执行。

## 17. 安全与审计

- KPI、评估、动作和申诉按租户隔离。
- 个人绩效数据只对本人、评估者、授权管理者和 Boss 可见。
- 非解雇高影响动作需要独立 AI 复核；解雇需要人类 step-up 批准。
- 原始证据不可修改。
- 所有拒绝、通过、执行和撤销都有审计。
- 绩效数据不进入公共知识库。
- 员工离职后绩效记录按保留策略归档，不默认公开。
- 这里的解雇是终止 AI 员工运行时和组织关系，不是解除人类劳动合同。
- Regent 不代替企业作出人类雇佣、薪酬或纪律决定；相关事项必须进入企业授权的 HR/法务流程。
