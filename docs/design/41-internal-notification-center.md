# 41 内部通知中心

- 版本：v0.1（待评审）
- 范围：仪表盘内部通知、分级路由、持久化、SignalR、去重和已读状态
- 对应需求：FR-024、FR-085、BR-143、BR-144
- 对应缺口：G-56

## 1. 范围

- 第一梯队只实现仪表盘内部通知中心。
- 不实现 Telegram、邮件、短信、Slack、飞书、企业微信、Teams 或通用 Webhook。
- 当前不保留通知 Provider 接口、外部渠道配置或外发兼容层。
- 外部通知如将来重新引入，必须作为新需求评审。

## 2. 权威记录

- Postgres 通知表是权威记录。
- SignalR 只负责实时提示，不承载唯一通知事实。
- 每条通知属于一个租户和一个接收人。
- 实时连接断开后，用户重新进入页面或主动刷新即可从数据库重拉。

## 3. 分级路由

| 级别 | 场景 | 站内行为 |
|---|---|---|
| L0 | 普通指标波动 | 仅记录，不生成个人通知 |
| L1 | 单次失败、轻微延迟 | 进入摘要或趋势 |
| L2 | 预算预警、任务异常、依赖阻塞 | 立即生成通知并提示相关负责人 |
| L3 | 硬预算、密钥风险、服务不可用、跨租户风险 | 立即通知 Owner、值班负责人和 Controller |
| SEV1/SEV2 | 安全事件 | 立即通知 Boss、IC 和受影响租户负责人 |

- P0/P1 审批和阻断事项立即进入站内通知中心。
- 普通 P2/P3 消息按 Q-041 工作窗口进入队列或摘要。
- L3/SEV1 不受普通静默时段限制。
- 定时报告按用户设置时间生成，未设置时默认 09:00。

## 4. 接收人与权限

- Owner、Co-Owner、事件负责人、IC 和值班接收人按租户配置。
- 接收人必须拥有对应事件范围的查看权限。
- 通知列表和详情在服务端再次鉴权，不能只靠前端隐藏。
- 运营人员只能查看授权运维通知，不能自动获得租户业务通知。
- 权限撤销后立即停止新通知投递，历史记录按保留策略处理。

## 5. 通知内容

外部通知不实现，内部通知仍遵循最小披露：

- 通知 ID、租户、级别、类型和发生时间。
- 简短标题和已确认影响。
- 需要采取的动作。
- 授权详情链接。
- 关联事件、任务、项目或事件响应 ID。

禁止写入：

- 密钥、Token、密码和验证码。
- 完整 Prompt、源码、原始日志和堆栈。
- 未脱敏 PII 和客户数据。
- 密封评测集。
- 带凭据的 URL。

 Butler 可以生成摘要，但通知服务仍执行 DLP、内容安全和权限检查。

## 6. 状态机

```text
Pending → Available → Read
              └→ Acknowledged
              └→ Archived
              └→ Suppressed
```

- `Pending`：事件已持久化，等待投影和实时提示。
- `Available`：接收人可检索。
- `Read`：用户已查看。
- `Acknowledged`：需要确认的事项已确认。
- `Archived`：用户归档，不删除审计。
- `Suppressed`：被确定性去重或抑制规则合并。

审批请求的 `Acknowledged` 不表示批准；正式决定仍走审批 API。

## 7. 投递语义

- 业务事件与通知写入同一事务的 Outbox。
- Dispatcher 使用 `SKIP LOCKED` 批量处理。
- 至少一次投递，接收人维度使用 Inbox 或唯一约束去重。
- 幂等键为 `(tenant_id, event_id, recipient_id, notification_type)`。
- SignalR 推送失败不影响通知持久化。
- 客户端使用 `after_id` 或游标增量拉取，断线重连后补齐。
- 同一事件更新只更新当前通知版本，历史变更进入审计。

## 8. 去重、分组与抑制

- 相同根因、相同接收人和相同时间窗口的告警合并。
- 抑制窗口和分组键版本化。
- 升级为更高级别时更新严重度，不生成无意义重复通知。
- 已解决事件生成关闭通知，不删除原通知。
- 抑制记录保留原因、规则版本和命中次数。

## 9. 重试与死信

- 通知投影失败使用指数退避重试。
- 默认最多重试 5 次，之后进入内部死信队列并告警。
- 死信不等于丢失，可由运维或授权服务重放。
- 重放使用相同幂等键，不重复生成通知。
- SignalR 不使用数据库死信机制，连接失败直接依赖客户端重拉。

## 10. 实体

- `Notification`：租户、接收人、级别、类型、内容、状态和关联对象。
- `NotificationDelivery`：站内投影、SignalR 尝试和重拉游标。
- `NotificationPreference`：接收人、级别、摘要和免打扰偏好。
- `NotificationSuppression`：去重和抑制规则及命中记录。

## 11. API

- `GET /notifications?after_id={id}`：增量拉取。
- `GET /notifications/{id}`：获取授权详情。
- `POST /notifications/{id}/read`：标记已读。
- `POST /notifications/{id}/acknowledge`：确认需要处理的事项。
- `POST /notifications/{id}/archive`：归档。
- `GET /notification-preferences`：读取偏好。
- `PUT /notification-preferences`：更新偏好。
- 普通员工不能调用发送通知的管理接口。

## 12. 指标

| 指标 | 目标 |
|---|---:|
| 内部通知可检索率 | 100% |
| 重复内部通知数 | 0 |
| L3/SEV1 站内可见延迟 | ≤5 秒 |
| 超过 15 分钟未处理通知死信 | 0 |
| 通知正文秘密泄漏数 | 0 |
| 越权通知访问数 | 0 |

## 13. 测试场景

1. 业务事件提交后即使 SignalR 断开也能从数据库拉取通知。
2. 同一事件重复投递只生成一条通知。
3. 不同接收人分别获得授权通知。
4. 撤销权限后不再生成新通知。
5. 越权用户不能读取其他租户或范围外通知。
6. L3/SEV1 不受普通静默时段限制。
7. P2/P3 通知遵守 Q-041 工作窗口。
8. 告警升级更新严重度而不重复刷屏。
9. 已解决事件生成关闭通知。
10. Acknowledge 不构成审批。
11. 通知正文包含秘密时拒绝写入。
12. Butler 摘要不能绕过 DLP 和内容安全检查。
13. 投影重试耗尽后进入死信且可重放。
14. 重放不重复生成通知。
15. 外部渠道配置请求返回明确不支持错误。

## 14. 验收场景

1. 第一梯队只有仪表盘内部通知中心。
2. 所有通知可持久化和重新检索。
3. SignalR 只是实时增强，不是唯一投递路径。
4. 分级、去重、授权和已读状态完整。
5. 不实现 Telegram、邮件、其他 IM 或 Webhook。
6. 通知不包含秘密，也不替代正式审批。
